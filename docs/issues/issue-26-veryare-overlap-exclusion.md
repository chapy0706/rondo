# issue-26: veryare 被り判定と固定骨格ステージ

## 背景

隠れ側同士の「被り」判定と、ステージ構成を実装する（ADR 0026・ADR 0032）。

当初は禁止エリア方式（ADR 0026）、続いて全域木による迷路生成（ADR 0031）を検討したが、最終的に「廊下の骨格を10種類あらかじめ用意し、各骨格内の部屋スロットにランダムに部屋タイプを割り当てる」方式に落ち着いた（ADR 0032）。廊下が既知の固定構造であるため、到達可能性を保証するアルゴリズムが不要になり、実装が単純になる。

被り判定（プレイヤー同士の球体コリジョンの重なり）は、この一連の変更の影響を受けず、ADR 0026 のまま実装する。

## スコープ

### このissueでやること

- プレイヤーへの球体コリジョンの実装
- 準備移動フェーズ終了時、全員の座標から被りをサーバーが判定し、重なっていたプレイヤーを失格にする
- **骨格データの定義**: 10種類の廊下骨格を、データとして定義する（実際の3Dモデルとしての作り込みは issue-29）。各骨格は、廊下の経路と、廊下に面した部屋スロットの位置を持つ。縦長の屋敷を想定する。スロットは大小2種類のサイズを持つ
- **骨格のランダム選択**: ゲーム開始時、10種類の骨格から1つをランダムに選ぶ
- **部屋タイプのランダム割り当て**:
  - 大スロットには、「和室単体」「和室＋押し入れ」「和室＋掛け軸エリア」のいずれかをランダムに割り当てる。**掛け軸エリアは見た目だけの装飾とし、隠れる機能は持たせない**（当たり判定・座標データとしては部屋全体の一部として扱う）
  - 小スロットには「押し入れ単体」（廊下に直接面した独立押し入れ）を割り当てる
  - スロットは、何も割り当てず空きのままにすることも許容する（生成のたびの密度に濃淡を持たせる）
  - 全体の構成は、和室8〜12室程度、押し入れ（部屋内包・独立の両方を合わせて）4室前後、縁側1、玄関1（固定）に沿うようにする
  - 玄関は固定位置とし、鬼と隠れ側の両方の初期リスポーン位置とする
  - 縁側は隠れられるが、外周（庭側）には見えない壁を設け、そこから出られないようにする
- **到達可能性**: 部屋の出入り口（襖の設置位置）は、廊下に面した各スロットにつき1つ定義する。部屋内包の押し入れ・掛け軸エリアは、その部屋の内部からのみ入れる構造とし、廊下に別の襖は定義しない。部屋同士を直接繋ぐ襖も定義しない
- **ステージ整合性の静的テスト**: 以下をテストで検算する
  - 10種類の骨格データが、いずれも部屋スロットが廊下に面していること
  - 各スロットの出入り口（襖）が1つだけであること。部屋内包の押し入れ・掛け軸エリアには、廊下側の襖が別途定義されていないこと
  - 部屋同士を直接繋ぐ襖が定義されていないこと
  - 各骨格が、想定する部屋タイプの構成（和室8〜12・押し入れ4前後・縁側1・玄関1）に沿っていること
  - 玄関の位置が骨格ごとに固定であること
  - 骨格の選択と部屋タイプの割り当てが、実行のたびに変わりうること（空きスロットが生じることも含む）
- **エッジケースのテスト**: プレイヤーの動きを想定した境界条件をテストで検証する
  - 準備移動フェーズ終了時、ほぼ同座標に複数人がいる場合、全員が被り判定に含まれるか（2人だけでなく3人以上のケースも）

### このissueでやらないこと

- 当たり判定（issue-27。射撃時の命中判定は別の仕組み）
- ステージ・骨格・部屋タイプの見た目の作り込み、襖の実装、キャラクターとの統合（issue-29）
- 答え合わせタイムの演出（issue-29）
- ステージ選択機能そのもの（roomOptions への追加は issue-29）

## 設計方針

- 被り判定の方式は ADR 0026 に従う（変更なし）
- 骨格・部屋割り当ての方式は ADR 0032 に従う
- 被り判定はサーバー権威（各プレイヤーの座標をサーバーが持つ）で行う
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 準備移動フェーズ終了時、球体が重なっていたプレイヤー全員が失格になる
- 10種類の骨格データが定義され、いずれも部屋スロットが廊下に面している
- 大スロットに和室単体・和室＋押し入れ・和室＋掛け軸エリアのいずれか、小スロットに押し入れ単体が割り当てられ、空きスロットも許容される
- 各骨格が、和室8〜12・押し入れ4前後・縁側1・玄関1固定の構成に沿っている
- ゲーム開始時、骨格が10種類からランダムに選ばれる
- 選ばれた骨格の各スロットに、部屋タイプがランダムに割り当てられる（玄関は固定）
- 玄関が、鬼と隠れ側の両方の初期リスポーン位置として記録されている
- ステージ整合性テスト（部屋スロットの到達可能性、部屋間の非接続、構成の妥当性、選択・割り当ての非決定性）が通る
- エッジケースのテスト（3人以上の被り）が通る
- `make verify` が通る

## 段階

1. 10種類の骨格データ（廊下の経路、部屋スロットの位置）を定義する
2. 骨格のランダム選択と、部屋タイプのランダム割り当てをテストファーストで実装する
3. 部屋スロットが廊下に面していることを検算するテストを書く
4. プレイヤーの球体コリジョンを実装する
5. 準備移動フェーズ終了時の被り判定をサーバーに実装する（エッジケース：3人以上の同時被りを含めてテストする）
