# issue-62: 当日の運用メモ（runbook）

## 背景

発表会の当日、サーバー（A1）を、落ち着いて見守り、困ったときに、迷わず対応できる手順書が要る。開発中に作った道具（deploy/a1-deploy.sh、tools/verify.sh、tools/bots.sh など）と、docs/deploy.md の手順を、当日の目線で、1 か所にまとめる。

手順は、A1 で実際に動かして確かめたものだけを、書く。動かしていない手順は、「未確認」と書く。そのため、本 issue の仕上げは、A1 への載せ換え（土日）の後になる。

## スコープ

### このissueでやること

- docs/runbook.md（絵文字なし）を書く。次の 5 つの節を、そろえる
  1. 開場前のチェックリスト: デプロイ後の自動確認（tools/verify.sh --web … --ws … --assets …）、ブラウザで 2 タブの通し、スマホ 1 台の通し、素材の配信（manifest と glb）、時刻と通信の確認、ハートビートの確認（ブラウザの開発者ツールで、ping と pong）
  2. 稼働中の見方: Grafana などで見る数値（ルーム数、接続数、メモリ、エラーの数）と、しきい値の目安。docker logs の見方（rondo-ws のエラーの連続、受信プロセスが落ちた行（電文の上限）、OTP の警告）
  3. 困ったときの対応（症状ごと）: ルームが消えた、満員で入れない、素材が出ない（仮の表示になる。警告は出ない設計）、画面が固まる・つながらない、サーバーを再起動する、戻す（git revert と再デプロイ、動的設定を控えに戻す、manifest を控えに戻す）。コマンドは、そのまま貼れる形で書く
  4. やってはいけないこと: 発表会の最中のデプロイ、素材の差し替え、env ファイルの変更、同時ルーム数や定員の変更
  5. 終了後: サービスを止める、または閉じる手順（10/31〜11/1。web のコンテナを止める、または認証をかける）、素材の扱い、ログの保存
- 連絡の流れ（誰が、何を判断するか）は、人が書く欄として、空欄で用意する
- スマホで見られる短縮版（1 画面。docs/runbook-card.md）: 最初に見る 5 項目（つながらない、素材が出ない、再起動、戻す、連絡先）だけ
- 手順の確かめ
  - 各手順に、「確認済み（日付）」または「未確認」を付ける
  - A1 での確認は、人が実行する。実行するコマンドと、貼ってほしい出力を、一覧にして、報告する

### このissueでやらないこと

- 監視の通知の自動化（Prometheus のアラートなど）
- 運用の自動化（自動再起動のスクリプトなど。コンテナの restart: unless-stopped は、すでにある）
- 当日の人員の割り当て

## 設計方針

- 読む人は、焦っている。症状から引ける形にし、最初の 1 行で、何をすべきかが分かること
- コマンドは、コピーして貼れる形（変数は、先に定義して見せる）で、危険な操作（コンテナの削除など）は、含めない。含める場合は、理由と、戻し方を添える
- 秘密の値（env ファイルの中身）は、書かない（場所だけを書く）
- 手順は、docs/deploy.md と食い違わない（同じ手順は、リンクで参照する）

## 受け入れ条件

- docs/runbook.md に、5 つの節が、そろっている
- 各手順に、「確認済み（日付）」または「未確認」が付いている
- 症状ごとの対応が、少なくとも 6 つ（上の例）ある
- 短縮版（runbook-card.md）が、スマホの 1 画面に収まる
- docs/deploy.md の手順と、食い違わない（Claude Code が、差分を確かめる）
- 秘密の値が、書かれていない（grep で確かめる）
- `make verify` が通る（文書の変更のみ）

## 段階

1. 既存の docs（deploy.md、assets.md、e2e.md、bots.md）と、道具の一覧を読み、runbook の構成と、症状の一覧を提案して、一度止まる
2. runbook.md と、短縮版の下書きを書く（確認は、すべて「未確認」のまま）
3. A1 への載せ換えの後、人が実行する確認のコマンドと、貼ってほしい出力の一覧を、報告にまとめる
4. 人の確認の結果を受けて、「確認済み」に直す。見つかった食い違いを、直す
