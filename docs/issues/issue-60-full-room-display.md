# issue-60: 満員のときの表示

## 背景

同時ルーム数は 3、定員は 5 人（issue-66 で 8 人にするなら、その値）。発表会で来場者が増えると、ルームに入れない人、ルームを作れない人が出る。いまは、サーバーが返すエラーの種類（満員、ルームがいっぱいなど）を、利用者向けの文言に直す仕組みがなく、入れないときに、理由と、次にすることが分からない。

本 issue では、入れないときに、理由と、次の行動が、分かる画面にする。

## スコープ

### このissueでやること

- ロビーのルーム一覧
  - 満員のルームは、「満員」と出し、参加を押せない形（灰色）にする
  - 一覧を、一定の間隔（定数。5 秒程度）で、自動で更新する（空きが出たら、押せるようになる）。更新の失敗は、黙って次の機会に回す（画面を壊さない）
  - 参加を押した直後に、満員になっていた場合（競合）は、「ちょうど満員になりました」と出し、一覧を取り直す
- ルームを作れないとき（同時ルーム数の上限）
  - 「いまは、ルームがいっぱいです。少し待つか、ひとり用のゲームで遊んでください」と出す
  - ひとり用のゲームへの導線（選択画面へ戻るボタン、または、ひとり用のゲームの一覧）を出す
- エラーの文言
  - サーバーが返すエラーの種類（満員、ルームがいっぱい、参加済み、接続できない、ほか）を、やさしい日本語の文言と、次の行動の案内に直す。対応表は、クライアントの 1 か所に持つ
  - 知らない種類のエラーは、「うまくつながりません。もう一度お試しください」の形に落とす
  - サーバーのエラーの種類と契約は、変えない
- 純粋関数（エラーの種類から、文言と次の行動を決める、一覧の状態（満員、参加できる）の判定）は、テストを先に書く

### このissueでやらないこと

- 定員とルーム数の上限の変更（issue-66 の範囲）
- 順番待ちの予約、通知
- ゲーム固有のロジックの変更
- サーバーと契約の変更

## 設計方針

- 利用者向けの文言は、サーバーではなく、クライアントの 1 か所に持つ
- 自動更新は、画面が見えているときだけ動く（見えなくなったら止める）。通信を増やしすぎない
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 満員のルームが、一覧で、押せない形で出る。空きが出たら、自動で押せるようになる（テストで確認）
- ルームを作れないとき、案内と、ひとり用のゲームへの導線が出る（テストで確認）
- サーバーのエラーの種類が、すべて文言に対応する。未知の種類は、既定の文言に落ちる（テストで確認）
- 参加の競合（押した直後に満員）で、画面が壊れず、一覧が取り直される（テストで確認）
- 画面が見えていないとき、自動更新が止まる（偽の可視状態で確認）
- 目視: ルームを 3 つ作ったあと、4 つ目を作ろうとして、案内が出る。満員のルームに、入れない表示が出る
- `make verify` が通る

## 段階

1. 現在のエラーの種類と、ロビーの一覧の作りを調べ、画面と文言の案を提案して、一度止まる
2. 文言の対応表と、一覧の状態の判定を、テストを先に書いて実装する
3. ロビー（満員の表示、自動更新、競合の扱い）と、作れないときの案内を実装する
4. ボットと E2E に、ルーム 3 つ作成後の 4 つ目の拒否を足す
5. 目視で確かめる項目を、報告にまとめる
