# issue-48: 実接続の一発起動と、2タブのE2Eスモークテスト

## 背景

issue-40・41・42・47 は、単体テストと結合テストは通っているが、ブラウザでの2タブの確認が手作業で、手順が多く、まだ行えていない。マイルストーン1（10/10〜12）までに、同じ確認を何度も繰り返すことになるため、確認そのものを軽くする。

目的は2つある。

- 実接続の開発環境を、1コマンドで起動できるようにする
- 主要な流れ（入口、参加、状態の同期、切断と復帰、ハートビート）を、2つのブラウザで自動で確かめる

## スコープ

### このissueでやること

- 1コマンドでの起動
  - `make dev-all`（名前は既存の Makefile に合わせてよい）で、Gleam サーバー（ポート固定）と web（実接続、ポート固定）を同時に起動する
  - 終了すると、両方が止まる
  - WebSocket の URL は、起動するコマンドが渡す（手で環境変数を付けなくてよい）
- E2E スモークテスト（Playwright、2つのブラウザコンテキスト）
  - シナリオ1（入口と同期）: 選択画面で、タブ A が「新しく遊ぶ」、タブ B が「ルームに参加する」から同じルームに入る。待機ルームの円の色が、両方で揃って変わる（赤、緑、青）
  - シナリオ2（切断と復帰）: タブ B を一時的にオフラインにし、猶予内にオンラインへ戻すと、同じルームに復帰する。猶予を過ぎると、離脱が確定し、失敗の表示が出る
  - シナリオ3（ハートビート）: WebSocket のフレームを観察し、ping が約20秒ごとに届き、pong を返していることを確かめる
  - シナリオ4（接続の失敗）: 通信を遮断したまま「新しく遊ぶ」を押すと、約10秒後に失敗の表示が出る。通信を戻して「もう一度」で入れる
  - シナリオ5（結果まで）: 鬼選出から結果画面まで進む。所要時間が長い場合は、テスト用にフェーズ時間を縮める手段を提案し、報告に書く（サーバーの設定で縮めるなら、本番の既定は変えない）
- `make e2e` で実行できるようにする。`make verify` には含めない（時間とブラウザに依存するため）
- 手作業で確認する項目の一覧（自動化できないもの）を、docs に短くまとめる

### このissueでやらないこと

- ゲーム固有のロジックの変更
- 本番（Cloudflare 経由）の確認の自動化。手順は issue-41 の報告にある
- CI（Woodpecker）への組み込み
- 見た目の確認（スクリーンショットの比較）

## 設計方針

- テストを安定させるため、待ち時間は固定の秒数ではなく、画面の状態（円の色、表示の文言）を待つ
- 画面の要素を特定するための属性（data-testid など）の追加は許可する。ゲームの挙動は変えない
- 時間のかかるシナリオ（結果まで）は、分けて実行できるようにする
- テスト用の設定（フェーズ時間の短縮など）は、環境変数で有効にし、既定では無効にする

## 受け入れ条件

- `make dev-all` で、サーバーと web が起動し、終了で両方止まる
- `make e2e` で、シナリオ1〜4が通る。シナリオ5は、通る、または、通らない理由と必要な追加作業が報告されている
- 通常の `make verify` の時間が、大きく増えていない
- 手作業の確認項目の一覧が、docs にある
- `make verify` が通る

## 段階

1. 既存の Makefile、起動手順、ポートの使い方を読み、起動の方式を提案する
2. 起動のコマンドを作る
3. Playwright を導入し（devDependency）、シナリオ1を通す
4. シナリオ2〜4を足す
5. シナリオ5の方式を提案し、可能なら実装する
6. 手作業の確認項目を docs にまとめる
