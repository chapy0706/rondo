# issue-70: 終わったルームの自動閉鎖

## 背景

issue-51 の上限の試験で、終わったルームが、人が残っている間、同時ルーム数（3）に数えられたままになる問題が見つかった。ADR 0045（下書き）で、終わったルームは、数えない形に直した。

これで、結果画面のまま置かれたルームが、新しいルームの作成を妨げることはなくなった。ただし、終わったルームそのものは、中に人が残っている限り、サーバーに残り続ける（ルームのプロセス、接続、メモリ）。発表会の当日、スマホが結果画面のまま、置かれることは、よく起きる。終わったルームが、1 日のあいだに、溜まっていくのを防ぐ。

## スコープ

### このissueでやること

- 結果が確定してから、一定の時間（定数。例: 3 分）がたったら、サーバーが、そのルームを閉じる
  - 閉じるとき、残っている参加者（と観戦者）に、「ルームを閉じました」という通知を送り、接続は残したまま、ルームから外す。復帰トークンは、無効にする
  - 参加者が全員退出したときに閉じる、これまでの動きは、そのまま
  - 時間は、テストで差し替えられる形にする（環境変数での短縮も、フェーズ時間の短縮と同じ仕組みで）
- クライアント
  - 結果画面に、「あと ○ 秒で、ロビーへ戻ります」と、小さく出す（閉じるまでの残り時間。サーバーの閉じる時刻に合わせる。通知の形は、既存の通知の範囲で足りるかを、先に調べる）
  - 「ルームを閉じました」を受けたら、ロビー（または選択画面）へ戻す。戻ったあとに、「前のルームは、閉じられました」と、短く出す
  - 結果画面の「退出する」「ゲーム選択へ戻る」は、これまでどおり
- 台帳（room_directory）
  - 閉じたルームを、台帳から消す。終わったルームは、すでに数えない（ADR 0045）。閉じたあとの数え間違いがないことを、テストで確かめる
- ボットと E2E: 終わったルームが、時間（短縮）で閉じ、参加者がロビーへ戻ること、人が全員退出した場合の動きが変わらないことを、確かめる

### このissueでやらないこと

- 再戦（同じ参加者で、もう一度遊ぶ）
- ゲームの進行中のルームの閉鎖
- 結果の保存、記録

## 設計方針

- ルームを閉じる判断は、サーバーが持つ。クライアントの表示は、表示だけ
- 閉じる時刻は、「結果が確定した時刻 + 定数」。ルームのタイマーで行い、ルームが落ちても、台帳と接続アクターが、あとで掃除できる形を保つ（ADR 0045 の、台帳への通知と、矛盾しない）
- 閉じるときの通知と、復帰トークンの無効化は、純粋関数と結合テストで、先に確かめる
- 契約の変更は、必要最小限（既存の通知で足りるかを、先に調べる）。外側の電文を変える場合は、省略できる項目の追加だけ
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 結果が確定してから、定数の時間がたつと、ルームが閉じ、残っている参加者に通知が届く（結合テストで確認）
- 閉じたルームの復帰トークンでは、復帰できない（テストで確認）
- 閉じたルームが、台帳に残らず、同時ルーム数にも、数えられない（テストで確認）
- 参加者が全員退出したときの動きが、変わらない（既存のテストが通る）
- 結果画面に、残り時間が出て、閉じられると、ロビーへ戻る（テストと目視）
- 進行中のルーム（結果が出る前）は、閉じられない（テストで確認）
- `make verify` が通る

## 段階

1. 終わったルームの現在の扱い（ルームの状態、台帳、接続アクター、通知）を調べ、閉じる仕組みと、通知の形を提案して、一度止まる
2. 閉じる判断と、通知の組み立てを、テストを先に書いて実装する
3. ルーム、台帳、接続アクターの連携を実装し、結合テストを書く
4. クライアントの表示（残り時間、戻る処理、案内）を実装する
5. ボットと E2E を足し、目視で確かめる項目を、報告にまとめる
