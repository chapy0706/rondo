# issue-34: 鬼 CPU

## 背景

鬼 CPU（ADR 0038）を実装する。発表で鬼視点と隠れ視点の両方を1台で説明でき、一人での動作確認にも使える。issue-33 の基盤の上に作る。

## スコープ

### このissueでやること

- **探索**: 玄関から出発し、部屋スロットの襖を、ランダムな順の深さ優先（または幅優先）で巡る。一定の確率で襖を飛ばしたり再訪したりして、精度を粗くする。襖の前で開け、開けた襖は開けっぱなしにする（ADR 0033）
- **移動**: 探索フェーズの間、0.5秒ごとに1ステップ進む。歩く速さはパラメータにする。鬼の位置・向き・ポーズを、人間の鬼と同じ形で観戦者へ継続配信する
- **視界**: CPU ごとに、視野角と視距離を、決められた範囲の乱数で決める。壁と閉じた襖を遮るものとして、マス目の上で見通しを判定する（純粋関数）
- **発見判定**: 視界に入った隠れ側に対し、0.5秒ごとに乱数を引く。発見確率は、距離が近いほど高く、溶け込み度（issue-33 の色の差）が高いほど低い。0 にならない下限を設ける。成功したら、既存の「見つけた」処理を呼ぶ
- **見逃しポイント用の視界報告**: 鬼 CPU の場合、上記と同じ見通しの判定を使って、サーバーが「視界に入っている隠れ側」を求める（issue-32 と繋ぐ）
- **強さのプリセット**: 歩く速さ、視野角と視距離の範囲、発見確率、探索の粗さの組を、「よわい／ふつう／つよい」の3つとして定義する。ルーム作成時の選択肢（roomOptions）から選べるようにする
- **シミュレーションの仕組み**: 鬼 CPU と隠れ CPU だけの対戦を、画面なしで高速に回せるようにする（例: `make simulate`）。骨格10種 × 強さ3種 × 種を変えた数百〜数千回を実行し、次を集計して表で出力する
  - 隠れ側の勝率、見つかるまでの平均時間
  - ゲームが時間内に終わった割合
  - 異常の検出: フェーズが進まなくなった、壁や閉じた襖の向こうを見つけた、被りの失格が想定と違う、「まだ隠れている」集合が増えた、など（ADR 0028 の条件をそのまま判定に使う）
- 歩く速さ・視野・発見確率は、この集計を見て調整する。骨格ごとの偏りが大きいものがあれば、報告に含める

### このissueでやらないこと

- 襖の実際の開閉の見た目（issue-29）
- 人間の鬼の操作・射撃（issue-27）

## 設計方針

- ADR 0038・0035・0028 に従う
- すべて純粋関数と種付きの乱数で実装し、テストは決定的にする
- 発見処理は、人間の鬼が当てた場合と同じ経路に繋ぐ。勝敗・観戦・ポイントの仕組みを CPU のために変えない
- 受け入れの基準は ADR 0028 に従う。CPU が隠れ側の位置を「意図せず知っている」状態（壁越しの発見など）にならないよう、見通しの判定を守る

## 受け入れ条件

- 鬼 CPU が玄関から出て、襖を順に巡る
- 壁や閉じた襖の向こうの隠れ側を、見つけることがない（テストで確認する）
- 視界に入った隠れ側を、距離と溶け込み度に応じた確率で見つける。溶け込み度が高いほど見つかりにくいが、0% にはならない
- 発見が、既存の「見つけた」処理を通り、観戦・勝敗に反映される
- 種を固定すれば、同じ動きになる
- シミュレーションの集計が出力され、異常の検出が0件である
- 強さのプリセットごとに、鬼の強さの順（よわい < ふつう < つよい）が勝率に表れている
- どの骨格でも、どちらかが常に勝つ状態になっていない
- `make verify` が通る

## 段階

1. 見通しの判定（マス目、壁・閉じた襖で遮蔽）を、テストファーストで実装する
2. 探索の経路（ランダムな深さ優先、粗さのパラメータ）を実装する
3. 移動と、襖を開ける動作を、0.5秒ごとのステップとして実装する
4. 視野角・視距離の乱数と、発見判定を実装する
5. 既存の「見つけた」処理と、見逃しポイント用の視界報告に繋ぐ
6. 強さのプリセットと、シミュレーションの仕組みを実装する
7. 集計を見て、パラメータを調整する
