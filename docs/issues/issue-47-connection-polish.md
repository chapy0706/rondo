# issue-47: 接続まわりの仕上げ（入口・タイムアウト・取り残しの防止）

## 背景

issue-40 で、ロビーからゲーム画面へ移れるようになり、接続とルームの状態はタブに1つのセッション（RealtimeSession）が持つようになった。発表会で来場者が実際に遊ぶ場面を考えると、次の3つが残っている。

- 選択画面から veryare を選ぶと、いつも新しいルームが作られる。2人目以降が、既存のルームに参加する入口が、選択画面にない。同時ルーム数は3なので、すぐ上限に当たる
- 実接続で再接続がすべて失敗したとき、「ルームに接続中...」のまま止まる。会場の通信は不安定になりやすい
- 参加・作成の返事が届く前にゲーム画面を離れると、後から届いた room-joined で、画面がないのにルームに入ったままになる。接続は切れていないので、再接続の猶予（ADR 0013）も働かず、定員5人の枠を塞ぐ

マイルストーン1（10/10〜12）の前に入れる。

## スコープ

### このissueでやること

- 選択画面の入口を2つにする
  - 「新しく遊ぶ」: 従来どおり、ルームを作成して入る
  - 「ルームに参加する」: ロビー（/lobby/<ゲーム>）へ移る
  - 1人用のゲーム（テトリス、rolling、link、chess、czz など）は、入口を分けず、従来どおり
  - ロビーを出すのは、リアルタイム対戦のゲームだけにする。モックの場合も同じ導線で動く
- 接続のタイムアウトと再試行
  - 参加・作成・復帰の返事が一定時間（目安 10 秒）届かなければ、「つながりません」という文言と、「もう一度」「ロビーへ」「ゲーム選択へ」のボタンを出す
  - 再接続がすべて失敗したときも、同じ画面を出す。復帰先（resumeStore）は消す
  - 時間は、テストで差し替えられるようにする
- 取り残しの防止
  - 返事が届く前にゲーム画面を離れた場合、後から届いた room-joined を受け取った時点で、画面（購読者）がなければ、すぐに leave-room を送る
  - 作成の返事（ルームを作るリクエスト）でも同様に、画面がなければ退出する

### このissueでやらないこと

- ゲーム固有のロジックの変更
- サーバー側（Gleam）と契約（packages/contracts）の変更。必要になった場合は、理由を報告して止まる
- ロビーの見た目の作り込み
- 共通起動画面を挟むリアルタイムゲームの導線の見直し（veryare は自前の起動画面のため影響しない）

## 設計方針

- 状態の遷移（待機、接続中、参加済み、失敗、離脱済み）は、純粋な関数にまとめ、テストを先に書く
- 取り残しの防止は、セッション層（RealtimeSession）で行う。画面の付け外し（StrictMode を含む）に依存しない
- 失敗したときは、利用者に原因を説明しすぎない。次に何をすればよいかが分かる文言にする
- 受け入れの基準は ADR 0028 の考え方に沿い、進行停止（接続中のまま止まる）と、枠の取り残しを最優先で守る

## 受け入れ条件

- 選択画面で、リアルタイム対戦のゲームに「新しく遊ぶ」と「ルームに参加する」が出る。1人用のゲームには出ない
- 「ルームに参加する」から、ロビー経由でゲーム画面に入れる（2タブで確認）
- 返事が届かないとき、一定時間後に失敗の表示が出て、「もう一度」「ロビーへ」「ゲーム選択へ」が使える（テストで確認）
- 再接続がすべて失敗したとき、同じ失敗の表示が出る
- 返事の前に画面を離れても、後から届いた room-joined で、ルームに入ったままにならない（テストで確認）。サーバー側のルームの人数が戻る
- `make verify` が通る（TS・Gleam 双方）

## 段階

1. 状態の遷移を、テストを先に書いて実装する（タイムアウト、取り残しの防止）
2. セッション層に、タイムアウトと、遅れて届いた room-joined の扱いを入れる
3. 失敗の表示（PlayHost）を実装する
4. 選択画面の入口を、リアルタイム対戦のゲームだけ2つにする
5. 2タブでの確認手順を、報告にまとめる（通信を遮断する確認を含む）
