# issue-66: 最大 8 人と、CPU の数の設定

## 背景

いまの定員は 5 人で、同時ルーム数は 3（ADR 0030）。CPU は、ルーム作成の設定で選べるが、数は少ない。発表会では、人数の多い来場者グループが、1 つのルームで遊べると、場が盛り上がる。人が足りないときは、CPU で埋められると、遊びやすい。

本 issue では、定員を最大 8 人に広げ、CPU の数を、上限まで設定できるようにする。負荷の確認（issue-51）のあとに、上限の値を決めて入れる。

## スコープ

### このissueでやること

- 定員を 8 人にする（定数。人間と CPU を合わせた数）。同時ルーム数は、負荷試験の結果で決める（3 のまま、または上げる）
- CPU の数の設定（ルーム作成の設定）
  - 鬼は 1 人。鬼を、人間にするか CPU にするかを選ぶ（いまの仕組みのまま）
  - 隠れ側の CPU の数を、0 から、定員 − 人間の数 − 鬼 の範囲で選べる
  - 実際の CPU の数 = 設定した数と、空き枠（定員 − 人間の数）の、小さいほう。人間が入ってきたら、CPU が 1 体減る（人間を優先する）。減った CPU は、準備移動の開始までに、確定する
- 待機ルーム
  - 席の輪を 8 席にする（広さ 3.5 m で、席の間が窮屈でないかを、確かめる。足りなければ、広さの値を提案する）
  - 他のメンバーの体を、最大 7 体まで描く
- 描画の重さ（スマホ）
  - 同時に描く素材の人型（スキンつき）に、上限を設ける（近い 5 体まで。定数）。それより遠い体は、仮のカプセル（または、簡易な体）で描く。動きの更新は、見えている体だけ
  - 実機で、8 人が同時に動いても、重くならないことを確かめる
- 通信量
  - 待機の同期（8 人）、探索の開始の一括配信（隠れ側 7 人のペイントとポーズ）、結果の一覧が、いまの設計の目安（1 ルームあたり毎秒 50 通以下など）に収まることを、測って報告する
- ステージ
  - 隠れ側 7 人が、玄関に重なって現れる（ADR 0032）。準備移動で、別々の場所へ動けること、被り判定の既存の規則が、そのまま動くこと、隠れる場所の数（スロット）が足りることを、すべての骨格で、テストで確かめる
- 結果画面: 8 人ぶんの順位と詳細が、見やすく出ること
- ボットと E2E: 8 人のシナリオ（人間のボットと、CPU の混ざり方）を足す
- 負荷試験（issue-51）: 3 ルーム × 8 人（24 接続）と、CPU の計算の負荷。結果から、同時ルーム数と定員の上限を決める

### このissueでやらないこと

- 鬼を複数にすること
- 観戦（issue-67）
- ステージの新規作成
- 定員 8 を超える人数

## 設計方針

- 定員、CPU の数、同時ルーム数は、定数と設定で持ち、サーバーが正。クライアントの選択肢は、サーバーの上限に合わせる
- 契約の変更は、設定の値（CPU の数）の追加が、既存の settings の範囲で足りるかを、先に調べる。外側の電文は変えない
- 負荷の確認が先。上限の値は、実測から決める
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 定員 8 のルームで、人間と CPU が、合わせて 8 人まで入れる。9 人目は、満員で断られる（テストで確認）
- CPU の数の設定が、定員と人間の数に合わせて、正しく決まる。人間が入ると CPU が減る（テストで確認）
- すべての骨格で、隠れ側 7 人が、準備移動の間に、被らずに隠れられる（テストで確認。隠れる場所の数が足りること）
- 通信量の測定結果が、目安に収まる（報告に表）
- 3 ルーム × 8 人の負荷試験が通る（結果を報告）
- スマホの縦画面で、8 人が動いても、描画が重くない（目視。実機）
- 既存の人数（5 人以下）の動きが、変わらない（既存のテストが、変更なしで通る）
- `make verify` が通る

## 段階

1. 現在の定員、CPU の設定、同時ルーム数の扱いを調べ、変更の範囲と、負荷試験の方式を提案して、一度止まる
2. 負荷試験（issue-51 の 24 接続）を先に行い、上限の値を決める
3. 定員と CPU の数の設定を、テストを先に書いて実装する
4. 待機ルームの 8 席、体の描画の上限を実装する
5. ボット、E2E、通信量の測定を行い、目視で確かめる項目を、報告にまとめる
