# issue-49: ボット同士の対戦による、ブラウザなしの自動確認

## 背景

マイルストーン1までに、veryare の判定とフェーズの確認を何度も行うことになる。ブラウザを2〜3枚開く確認は重く、不安定になりやすい。サーバーの流れ（入室、鬼選出、準備移動、ペイント、探索、答え合わせ、結果）は、WebSocket のクライアントをプログラムで動かせば、ブラウザなしで通せる。

issue-31 で、2接続を使う確認用のスクリプトを作った実績がある。これを発展させ、5人分のボットで、ゲームの最初から最後までを自動で通す仕組みにする。

## スコープ

### このissueでやること

- ボットのクライアントを作る
  - 契約（packages/contracts）の電文を、そのまま使う
  - session の受け取り、表示名の設定、ルーム作成・参加、ゲームイベントの送信、ping への pong の返信
  - 動きは、シナリオとして宣言する（例: 「鬼希望エリアに入る」「ペイントする」「その場にとどまる」「切断する」）
- シナリオを作る（結果まで通すもの）
  - 時間切れで隠れ側の勝ち
  - 鬼の離脱（隠れ側の勝ち）
  - 鬼選出の時点で人数が足りず、不成立
  - 被りによる全員失格（鬼の勝ち）
  - 各シナリオで、全員のボットに game-ended が届くことと、順位・details が期待どおりであることを確かめる
  - 全員発見のシナリオは、issue-27（撃つ）ができてから足す
- フェーズ時間の短縮
  - サーバーに、テスト用にフェーズ時間を縮める設定を足す（環境変数。本番の既定は変えない）
  - 縮めたときも、判定の順序と結果が変わらないことを確かめる
- 実行方法
  - `make bots`（名前は Makefile に合わせてよい）で、サーバーを起動し、全シナリオを流し、結果を表で出す
  - 終了コードで、成功・失敗が分かる
  - `make verify` には含めない（サーバーの起動を伴うため）。ただし、実行時間が短ければ、含める案を報告に書く

### このissueでやらないこと

- ゲームの判定ロジックの変更
- ブラウザを使った確認（issue-48）
- 負荷や長時間の試験（issue-51）

## 設計方針

- ボットは、画面や three.js を使わない。契約の電文だけで動く
- 時間は、サーバーの設定で縮める。ボット側で時計を偽装しない
- シナリオは、宣言的に書き、後から追加しやすくする
- 乱数は種を指定できるようにし、失敗を再現できるようにする
- 限定配信（ADR 0021）の確認として、宛先でないボットに、隠すべき情報が届かないことも確かめる
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- `make bots` で、4つのシナリオがすべて通る
- 各シナリオで、全員（参加者）に game-ended が届き、内容が期待どおりである
- 宛先でないボットに、限定配信の内容が届かないことを、1つ以上のシナリオで確かめている
- フェーズ時間の短縮が、環境変数でのみ有効で、既定では無効である
- 実行時間が、全体で数分以内に収まる
- `make verify` が通る（TS・Gleam 双方）

## 段階

1. 既存の確認用スクリプト（issue-31 の two_clients.mjs など）と、契約の電文、ゲームイベントの形を読み、ボットの方式を提案する
2. フェーズ時間の短縮の設定を、テストを先に書いて実装する
3. ボットの土台（接続、session、ハートビートへの応答）を作る
4. シナリオを1つずつ足し、通す
5. 実行方法を整え、結果の表を出す
6. 手順と、シナリオの追加のしかたを docs にまとめる
