# issue-32: veryare 見逃しポイントといいね

## 背景

見つかった隠れ側の離脱を防ぎ、また、絶対に見つからないような不自然な場所へ隠れることを避けてもらうために、勝敗とは別の楽しみとして、見逃しポイントといいねを実装する（ADR 0036）。どちらも勝敗には一切影響しない。

## スコープ

### このissueでやること

- **見逃しポイントの計算**: 純粋関数として実装する。入力は、鬼との距離と、鬼の視界に入っているかどうか。0.5秒ごとの加算値を返す
  - 圏内（鬼から半径 仮に6m 以内）は +3、圏内かつ視界に入っている間は +15（加算ではなく、視界内は 15）
  - 距離による比率: 鬼の真横で 1.0、半径の端で 0.3 の線形の減少。整数に丸める
  - 半径・加算値・比率はパラメータにする
- **サーバーでの累積**: 探索フェーズの間、0.5秒ごとにまだ隠れている隠れ側へ加算する。見つかった時点で加算を止め、それまでのポイントは残す
- **鬼クライアントの報告**: 探索フェーズ中、0.5秒ごとに、視界に入っている隠れ側（壁越しを除く）をサーバーへ報告する。圏内の判定（距離）はサーバーが行う
- **答え合わせタイムの視点切り替え**: 各隠れ側の隠れ場所を中心とした TPS 視点（ADR 0034）へ、前後に切り替えられる
- **いいね**: 見ている隠れ側へ送るボタン。1人が同じ隠れ側に送れるのは1回まで（仮）、自分には送れない。隠れ側は受け取った数を見られる
- **結果の表示**: 隠れ側ごとの見逃しポイントといいねの数を表示する。基盤の結果の扱いへの繋ぎ方は、既存のリアルタイムゲームの結果（issue-14）に合わせる
- 永続化はしない（ADR 0019）

### このissueでやらないこと

- 鬼側のスコア
- 勝敗への反映（ポイントもいいねも、勝敗に影響させない）

## 設計方針

- ADR 0036・0035・0028 に従う
- 視界の判定は鬼のクライアントの報告を信頼する（性善説、ADR 0035）
- 勝敗は常に「まだ隠れている」人数のみで決まる（ADR 0024）。ポイントやいいねを変えても勝敗が変わらないことをテストで守る

## 受け入れ条件

- 見逃しポイントの計算が、圏内・視界内・距離の比率のテストを満たす
- 探索フェーズ中、圏内にいる間、0.5秒ごとにポイントが加算される。見つかった後は加算されない
- 視界に入っている間は、圏内だけの場合より高いポイントが加算される
- 答え合わせタイムで、各隠れ側の隠れ場所へ視点を切り替えられ、いいねを送れる
- 同じ隠れ側へ、1人が2回目以降のいいねを送れない。自分自身にはいいねを送れない
- ポイントやいいねが、勝敗の判定に影響しない（テストで確認する）
- 結果の表示に、ポイントといいねが含まれる
- `make verify` が通る

## 段階

1. 見逃しポイントの計算を、純粋関数としてテストファーストで実装する
2. サーバーでの累積（0.5秒ごと、見つかった時点で停止）を実装する
3. 鬼クライアントの視界報告を実装する
4. いいねのメッセージと、重複・自己送信の防止を実装する
5. 答え合わせタイムの視点切り替えといいねのボタンを実装する
6. 結果の表示に繋ぐ
