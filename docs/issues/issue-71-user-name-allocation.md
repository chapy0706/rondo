# issue-71: 表示名（userN）の番号を、空いている一番小さい番号から使い回す

## 背景

接続したときに、サーバーが付ける表示名（user + 番号）は、これまでに接続した回数を数える形になっていて、番号が戻らないと見られる。退出して、ルームが閉じたあとで、再び接続すると、他に 32 人もいないのに、user33 のような名前になる。ルーム名の既定（「user18のルーム」）や、待機ルームの頭上の名前にも出るため、発表会で、2 人しか遊んでいないのに、user33 と出ると、来場者が不思議に思う。

アカウントは持たない設計（ADR 0015）なので、人の情報は、サーバーに残らない。番号が増えても、メモリに溜まるとは限らないが、念のため、ユーザーごとのデータが溜まる所がないかも、あわせて確かめる。

本 issue では、表示名の番号を、**空いている一番小さい番号から使い回す**形に直す。見た目の問題の修正で、遊びの判定と契約には触れない。

## スコープ

### このissueでやること

- 調べる（先に、報告に書く）
  - 表示名を付けている所（モジュール、数え方、再起動で戻るか）
  - ユーザーごとのデータが、接続が終わったあとも、溜まっていく所がないか（台帳、表、ログ、ETS など）。あれば、場所と増え方
  - 切断の猶予（10 秒）と復帰で、同じ人の名前が保たれる仕組み
- 番号の管理を、1 つの窓口（番号の管理役）にまとめる
  - 新しい人には、空いている一番小さい番号を渡す
  - 退出（切断の猶予が過ぎて、離脱が確定したとき）で、その番号を空ける
  - 猶予の間は、番号を取っておく。復帰した人は、同じ名前で戻る
  - 同時に接続している人の間で、名前が重ならない
  - 名前の形は、これまでと同じ（user + 番号）
- 番号の管理役が、落ちたときと、再起動したときの扱いを決める（すでに接続している人の番号と、重ならないこと）。決めた内容を、ADR（番号は最新の次。下書き）に書く
- ルーム名の既定、待機ルームの頭上の名前、結果の一覧の名前が、新しい名前で出ること（既存の画面とテストは、変えずに通る）

### このissueでやらないこと

- 自分で名前を決められるようにすること（ニックネーム。通信の取り決め（契約）を変える必要があり、発表会のあとの別 issue とする）
- 名前の重複の許可、日本語の名前、名前の変更
- 勝敗の判定、契約の型、画面の見た目の変更

## 設計方針

- 契約は変えない。サーバーが付けるラベルのままにする
- 番号の管理は、1 つの窓口で行い、「確保」と「解放」の対を、純粋な部分（番号の選び方）と、プロセスの部分（窓口）に分ける。番号の選び方は、純粋関数にして、テストを先に書く
- 解放の漏れ（番号が、いつまでも、空かない）を防ぐ。接続が、どんな終わり方（ふつうの退出、切断の猶予切れ、プロセスの異常終了）をしても、番号が空くこと
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 3 人が接続して、1 人が抜けると、次に入る人は、空いた番号をもらう（テストで確認）
- 全員が抜けたあと、新しい人は user1 になる（テストで確認）
- 切断の猶予の間は、番号を取っておき、復帰した人は、同じ名前で戻る。猶予が過ぎると、番号が空く（テストで確認）
- 同時に、大量に（例: 200 接続）つないで、切っても、名前が重ならず、番号が、最小の空きから使われる（テストで確認）
- 接続のプロセスが、異常終了しても、番号が空く（テストで確認）
- ユーザーごとのデータが、溜まっていく所が、ないことが、確かめられている（見つかった場合は、直す）
- 既存のテストは、変更なしで通る（変える必要が出たら、止まって質問する）
- `make verify` が通る。`make bots`、`./tools/load.sh join` と `limits` が通る
- 目視: ロビーで、ルームを作り、退出して、また作ると、名前が増えない（user1 のまま）

## 段階

1. 調べて、報告する（上の 3 点）。ユーザーごとのデータが溜まる所が見つかったとき、または、契約の変更が必要になりそうなときは、止まって質問する。それ以外は、そのまま、段階 2 へ進む
2. 番号の選び方（純粋関数）と、窓口のテストを、先に書く
3. 窓口を実装し、接続の開始と終わりにつなぐ
4. 異常終了と猶予切れの確認、大量接続の確認
5. ADR（下書き）を書く。目視で確かめる項目を、報告にまとめる
