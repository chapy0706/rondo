# issue-29b: 襖の開閉の状態と通知、射撃の見通しの有効化

## 背景

issue-29（ステージ統合）を4本に分けたうちの2本目。issue-29a で、人間の移動が選ばれたステージの座標に乗り、壁で止まるようになる。ただし襖は開いている扱いのまま。

襖（ADR 0033）は開閉でき、開けたら開けっぱなし、探索の開始で全部閉じ、答え合わせタイムの開始で全部開く。準備移動の開始時は、全部開いている（隠れ側がボタンを押さずに部屋へ入れるようにする / ADR 0042）。いま、人間の鬼が開けた襖の状態はサーバーに届いておらず、鬼 CPU は自分だけの「開けた襖」を持っている。射撃の見通し（issue-27）も、実際のルームでは無効（`shot_sight: False`）のまま。

本 issue で、襖の状態をサーバーの1か所に持ち、移動・射撃の見通し・鬼の通知のすべてが同じ状態を使うようにする。

## スコープ

### このissueでやること

- 襖の開閉の状態（サーバーの状態機械が持つ、開いている襖の集合）
  - 準備移動の開始では全部開いている（ADR 0042）。探索の開始で全部閉じる。答え合わせタイムの開始で全部開く（ADR 0033）
  - 開けた襖は開けっぱなし（閉じる操作は無い）
  - 開ける報告（クライアント → サーバー。game-event の payload）: どの襖か（境 `{a, b}`）
  - 受け付ける条件: 準備移動・ペイント・探索のいずれか、報告した人がステージにいる、その境が戸の一覧の襖である、報告した人の位置が襖の境から 1.5 m 以内（定数。骨格でも平屋でも同じ）
  - 鬼 CPU が開けた襖も、同じ状態にまとめる（鬼 CPU だけの状態をやめる）
- 移動の規則（issue-29a）に、この状態を渡す。閉じた襖で移動が止まる
- 襖の通知（サーバー → クライアント）: 開いている襖の一覧。変わるたびに全員へ送り、途中参加・再接続の人にも送る
- 鬼の通知（`VeryareOniNotice`）の `openDoors` を、境 `{a, b}` の一覧に切り替える（`VeryareDoor` の `{corridor, slot}` をやめる）。中身は、ゲームの襖の状態
- 射撃の見通しを有効にする（`shot_sight: True`）
  - 見通しは、壁と閉じた襖が遮り、開いた襖が通す（いまの「襖は開いている扱い」をやめる）
- 契約（`packages/contracts/src/veryare.ts`）: 開ける報告 `VeryareOpenDoorEvent`、襖の通知 `VeryareDoorsNotice`、鬼の通知の `openDoors` の型。`ClientMessage` と `ServerMessage` の外側は変えない
- 共有の見本（valid・invalid）を作り、TS と Gleam の両方で読み込む
- クライアントは、鬼の通知の新しい形を読めるようにする（表示の作り込みは issue-29c）

### このissueでやらないこと

- クライアントの襖の表示と、開けるボタン（issue-29c）
- 見通しの一般化（いつも開いている戸・0.3 m のマス / issue-45）
- 答え合わせタイムの演出の見た目（issue-29d）

## 設計方針

- ADR 0022・0033・0035・0042（下書き）に従う
- 判定はすべて純粋関数で書き、テストファーストで進める
- 境（外部入力）では、開ける報告を unknown として検証してから扱う
- 勝敗の判定と、既存のフェーズの遷移は変えない（襖の状態の変化を、フェーズの切り替えの時点に足すだけ）
- 受け入れの基準は ADR 0028 に従う。閉じた襖・壁の向こうの相手に当たらないことを守る

## 受け入れ条件

### 自動で確かめること

- 襖の状態（テストを先に書く）
  - 準備移動の開始で全部開いている。探索の開始で全部閉じる。答え合わせタイムの開始で全部開く
  - 開けた襖は、次のフェーズの切り替えまで開いたまま
  - 開ける報告は、受け付ける条件（フェーズ、ステージにいる、襖である、1.5 m 以内）をすべて満たすときだけ通る。1.5 m ちょうどは通り、それより遠いと通らない
  - 鬼 CPU が開けた襖が、ゲームの襖の状態に入る
- 移動: 閉じた襖で止まり、開けた後は通れる
- 射撃の見通し
  - 壁越しの相手には当たらない
  - 閉じた襖越しの相手には当たらない
  - 開いた襖越し・同じ領域で見通せる相手には当たる
  - 実際のルームで有効になっている（既定が `True`）
- 襖の通知が、変わるたびに全員へ届き、途中参加・再接続の人にも届く（結合テスト）
- 鬼の通知の `openDoors` が境 `{a, b}` の一覧で、ゲームの襖の状態と一致する
- 共有の見本の valid を TS の型で書いた見本と一致させ、Gleam の decoder が valid を受け付け、invalid を拒む
- 被り判定・勝敗・フェーズの遷移・鬼 CPU の既存のテストが通る。シミュレーション（`make simulate`）の異常が0件
- `make verify` が通る（TS・Gleam 双方）

### 目視でしか確かめられないこと（実行が要る確認）

- `make bots` で、全シナリオが通る（「全員発見」は、見通しが有効になっても当たる場所に隠れ側がいる）

## 段階

1. 開ける報告・襖の通知・境の型の案を、共有の見本として書く
2. 襖の状態と開ける報告の判定を、テストを先に書いて実装する
3. 鬼 CPU の襖を、ゲームの襖の状態にまとめる。鬼の通知の `openDoors` を切り替える
4. 移動の規則と射撃の見通しに、襖の状態を渡す。見通しを有効にする
5. 襖の通知を、変化・途中参加・再接続で届ける
6. `make bots` の手順を報告にまとめる
