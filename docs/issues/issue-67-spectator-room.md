# issue-67: 観戦ルーム（CPU だけで始まる試合を、好きな視点で見る）

## 背景

issue-28 で、見つかった人が、鬼の視点で観戦する仕組みは、できている。本 issue では、これとは別に、「試合に参加せず、見るだけの人」のための観戦ルームを作る。

ルームを作るときに「観戦ルーム」を選ぶと、人間の参加者なしで、CPU だけの試合が、すぐに始まる（鬼は CPU、隠れ側は CPU。数は、設定で、最大まで）。来場者は、そのルームに、観戦者として入り、自分の好きなキャラクターの視点で、試合を見られる。発表会の会場の画面に、CPU の試合を映しておく、といった使い方もできる。

優先度は、必須の作業の後。issue-66（最大 8 人と CPU の数）の、負荷の結果を見てから決める。

## スコープ

### このissueでやること

- ルーム作成の設定に、「観戦ルーム」を足す（トグル）。選ぶと、次のようになる
  - 人間の参加者は入れない。ルームに入る人は、すべて観戦者
  - 作った瞬間に、試合が始まる（鬼選出を省く。鬼 CPU。隠れ側は CPU を、設定の数だけ）。人間の準備は要らない
  - 試合が終わったら、結果を数秒見せ、同じ設定で、次の試合が自動で始まる（骨格は、毎回、抽選し直す）。観戦者がいなくなって、一定時間（定数）たったら、ルームを閉じる
- CPU の隠れ側が、準備移動の間に、玄関から隠れ場所へ歩く（いまは、置き場所へ直接置いている場合は、歩く動きを足す。準備移動の時間内に着く。被らない。鬼 CPU の経路探索を、使い回す）。これで、観戦者に、隠れ側が歩く様子が見える
- 観戦者の扱い
  - 観戦者は、参加者ではない。定員に数えない。観戦者の数に、上限（定数。20 など）を設ける
  - サーバーが、観戦ルームの観戦者にだけ、観戦用の通知を送る。内容は、全員の位置・向き・ポーズ・ペイント、襖の状態、フェーズ、残り時間（約 10 回/秒以下。変わったときだけ）。veryare の payload の追加だけで、外側の電文は変えない
  - 観戦ルームでは、参加者がいないので、全員の位置を、観戦者に送っても、秘密は漏れない。観戦用の通知は、人間が参加するルームでは、出さない（テストで確かめる）
- 観戦の視点（クライアント）
  - 追うキャラクターを、選べる（一覧、または、画面のタップ）。切り替えは、いつでも
  - 追従カメラは、issue-28 の、鬼視点の仕組みを使い回す。壁の向こうに出ない守り（ADR 0043）は、そのまま
  - 見渡せる視点（全体を上から見る）も、任意で足す（提案して確認する）
  - 観戦者は、ゲームに操作を送らない（移動、射撃、襖を開ける、は、できない）。操作の部品は、出さない
- ロビー: 観戦ルームの一覧に、「観戦」と出す。押すと、観戦者として入る（外側の電文は、変えない。ルームの種類で、入り方が決まる）
- 設定: 隠れ側の CPU の数（issue-66 の上限まで）、ステージ（ランダム間取り、広い屋敷、平屋）、探索の時間

### このissueでやらないこと

- 人間が参加する対戦への観戦者の受け入れ（秘密の漏れ、「教えること」の問題があるため。遅れをつけた観戦などは、別 issue で設計する）
- 観戦者のチャット、リアクション
- 試合の録画、再生
- 観戦者が試合に途中参加すること

## 設計方針

- 観戦用の通知は、観戦ルームの観戦者にだけ、サーバーが送る。人間の対戦ルームでは、出さない。この境目を、テストで守る（ADR 0021、0035）
- CPU の試合は、既存の状態機械（フェーズ、判定）を、そのまま使う。人間がいない状態でも、止まらず、進むこと
- 自動の次の試合は、負荷を見て、回数と間隔の上限を決める（A1 の資源を、占めすぎない）。観戦者がいないとき、閉じる
- 純粋関数（観戦用の通知の組み立て、観戦者の追従先の選び方）は、テストを先に書く
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 観戦ルームを作ると、人間の参加者なしで、試合が始まり、結果まで進み、自動で次の試合が始まる（ボットで確認）
- CPU の隠れ側が、準備移動で歩き、時間内に、被らずに、隠れ場所へ着く（すべての骨格で、テスト）
- 観戦者が入ると、観戦用の通知が届き、全員の位置などが見える（ボットの観戦者で確認）
- 観戦用の通知が、人間が参加するルームには、出ない。参加者でない接続には、届かない（テストで確認）
- 観戦者は、操作を送れない。送っても無視される（テストで確認）
- 観戦者の数の上限が効く。観戦者が 0 人になって一定時間たつと、ルームが閉じる（テストで確認）
- 追うキャラクターの切り替えが、できる。壁の向こうが見えない（目視）
- 観戦者が 20 人でも、サーバーと通信が、目安に収まる（負荷試験の結果を報告）
- スマホの縦画面で、観戦が、重くない（目視。実機）
- 既存の対戦（人間が参加するルーム）の動きが、変わらない（既存のテストが、変更なしで通る）
- `make verify` が通る

## 段階

1. 観戦ルームの作り方（ルームの種類、人間の参加者がいない状態での、フェーズと判定の進み方）、観戦用の通知の形、CPU の隠れ側の歩き方、視点の仕組みの使い回しを調べて、提案し、一度止まる
2. CPU の隠れ側の、準備移動の歩きを、テストを先に書いて実装する
3. 観戦ルームの作成、自動の次の試合、閉じる条件を実装する
4. 観戦用の通知と、観戦者の扱いを実装する（サーバー、契約、共有の見本）
5. 観戦のクライアント（視点の選択、追従カメラ、操作の非表示）を実装する
6. ロビー、ボット（観戦者）、E2E、負荷の測定を行い、目視で確かめる項目を、報告にまとめる
