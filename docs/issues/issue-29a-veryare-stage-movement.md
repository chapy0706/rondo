# issue-29a: ステージの座標での移動の規則、玄関へのリスポーン、ステージの通知

## 背景

issue-29（ステージ統合）を、仮素材版として4本に分けたうちの1本目。サーバーの土台を作る。

いま、人間の移動は、仮の ±5 m の正方形（`game.gleam` の `stage_half`）に丸められている。一方、サーバーの地図（`stage.gleam`・`sight.gleam`）は、選ばれた骨格の座標（1マス 1 m、およそ (0,0)〜(13,40)）で持っている。座標が食い違うため、玄関からの出現（ADR 0032）、壁で止まる移動、射撃の見通し（issue-27 で作ったが無効）が、実際のルームで働かない。

本 issue で、人間の移動を、選ばれたステージの座標と同じ規則に乗せる。規則は、平屋（ADR 0039 / issue-44）でもそのまま使える形にする（マスの大きさ・原点・戸の一覧を入力に取る）。

## スコープ

### このissueでやること

- 移動の規則（純粋関数。サーバー）
  - 入力: マスの大きさ、原点、幅・奥行き、各マスの領域、戸の一覧（隣り合う2マスの境 `{a, b}` と、種類: 襖・いつも開いている・いつも閉じている）、開いている襖の集合
  - 同じ領域どうしの境は通れる。異なる領域どうしの境は壁で通れない。戸の一覧にある境は、いつも開いている戸と、開いている襖なら通れる
  - ある位置（点）から次の位置への移動で、通れない境を越えるなら、越える手前で止める（境に沿って滑らせる）。マスの角をちょうど通るときは、両脇がどちらも通れる場合だけ通す（見通しの判定と同じ、安全側の扱い / ADR 0028）
  - 歩けるマスの外へは出ない
  - 骨格（ADR 0032）を、この入力に写す口を作る（1マス 1 m、原点 (0, 0)、戸はスロットの襖だけ）。縁側と庭の境は通れない（見えない壁）
- `game.move` のステージの丸め（`stage_half` の正方形）を、この規則に置き換える。待機ルーム（円）はそのまま
  - 襖の開閉の状態は issue-29b で入れる。本 issue の間は、襖を開いている扱いにする（壁だけが止める。射撃の見通しの扱いと同じ）
- 玄関へのリスポーン（ADR 0032）
  - 隠れ側は準備移動の開始で、鬼は探索の開始で、骨格の `spawn`（玄関）に現れる。全員が同じ場所に現れる（いまの輪の並べ方と、鬼の (0, 4.5) をやめる）
  - 鬼 CPU・隠れ CPU の置き方は変えない
- ステージの通知（サーバー → クライアント。veryare の game-state の payload）
  - 地図のデータそのものを載せる: マスの大きさ、原点、幅・奥行き、各行（1文字が1マスの領域）、部屋の割り当て、戸の一覧（`{a, b}` と種類）、リスポーン位置
  - ステージが決まったとき（ルームの開始）に全員へ送り、途中参加の人と、再接続で戻った人にも送る（届け方はサーバーの内部の仕組み。契約の外）
  - クライアントに骨格のコピーは持たせない
- 契約（`packages/contracts/src/veryare.ts`）に、境 `VeryareEdge`（`{a, b}`）、戸の種類、ステージの通知 `VeryareStageNotice` を足す。`ClientMessage` と `ServerMessage` の外側は変えない
- 共有の見本（fixture）
  - ステージの通知の見本（valid・invalid）を作り、TS と Gleam の両方で読み込む（ADR 0009）
  - 移動の規則の入出力の見本（地図・戸・開いている襖・移動の前後の位置 → 止まる位置）を作り、Gleam で読み込むテストを書く。TS 側は issue-29c で同じ見本を読む
- ボット（`bots/`）の更新
  - 全員が玄関に現れるので、隠れ側のボットは、準備移動の間に別々の歩けるマスへ動く。マスは、ステージの通知から選ぶ（玄関から一直線にたどれる、別々のマス。選び方は純粋関数でテストする）
  - 「被りによる全員失格」は、隠れ側が玄関にとどまる形に直す
  - 「全員発見」は、玄関から射程 8 m の内側で、見通せるマス（issue-29b で見通しが有効になっても当たる場所）に隠れ側を動かす

### このissueでやらないこと

- 襖の開閉の状態、襖の通知、射撃の見通しの有効化（issue-29b）
- クライアントの表示と移動（issue-29c）。本 issue から issue-29c までの間は、ブラウザの見た目の位置と、サーバーの位置が食い違う。確認はボットで行う
- 平屋のデータ（issue-44）
- 見通しの一般化（issue-45）

## 設計方針

- ADR 0032・0033・0035・0042（下書き）に従う。ADR 0039（平屋）と同じ規則を、骨格にも使う
- 判定はすべて純粋関数で書き、テストファーストで進める
- 性善説（ADR 0035）。移動の報告を規則で確かめるのは、誠実なクライアントとの食い違いを防ぐため
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

### 自動で確かめること

- 移動の規則（テストを先に書く）
  - 壁を越える移動は、越える手前で止まり、境に沿って滑る
  - 戸の一覧で、いつも開いている戸と開いている襖は通れ、閉じた襖といつも閉じている戸は通れない（入力として与えて確かめる）
  - マスの角をちょうど通る移動は、両脇がどちらも通れるときだけ通る
  - 歩けるマスの外へは出ない。縁側から庭へは出られない
  - マスの大きさ・原点が 1 m・(0, 0) 以外でも（例: 0.3 m）同じ規則で動く
- 骨格を移動の規則の入力に写すと、歩けるマス・領域・襖が、`stage.gleam` の骨格と一致する（10種すべて）
- `game.move` が、ステージでは移動の規則を使う。待機ルームの円の丸めは変わらない。±5 m の丸めは残っていない
- 隠れ側は準備移動の開始で、鬼は探索の開始で、玄関に現れる
- ステージの通知
  - ルームの開始で全員に届き、途中参加・再接続の人にも届く（結合テスト）
  - 載っている地図のデータから、骨格の歩けるマスと戸が復元できる
  - 共有の見本の valid を TS の型で書いた見本と一致させ、Gleam の decoder が valid を受け付け、invalid を拒む
- 移動の規則の共有の見本を、Gleam のテストが読み、すべて期待どおりに止まる
- 被り判定・勝敗・フェーズの遷移の既存のテストが通る
- ボットの、別々のマスの選び方（純粋関数）のテストと、シナリオの宣言の整合のテストが通る
- `make verify` が通る（TS・Gleam 双方）

### 目視でしか確かめられないこと（実行が要る確認）

- `make bots` で、5つのシナリオがすべて通る（サーバーの起動を伴う。報告に、実行するコマンドと、失敗したときに貼ってほしい出力の範囲を書く）

## 段階

1. 移動の規則の入力の形と、契約（境・戸の種類・ステージの通知）の案を、共有の見本として書く
2. 移動の規則を、テストを先に書いて実装する（止める・滑らせる・角・歩けるマスの外）
3. 骨格を入力に写す口を作り、10種で一致を確かめる
4. `game.move` を置き換え、リスポーンを入れる
5. ステージの通知を、開始・途中参加・再接続で届ける
6. ボットを更新し、`make bots` の手順を報告にまとめる
