# issue-50: デプロイ後の自動確認

## 背景

docs/deploy.md には、デプロイ後に手で確かめる項目がある（コンテナの起動、内部応答、Traefik、外部からの応答、素材配信の CORS とキャッシュのヘッダ、WebSocket の接続）。手で行うと抜けやすく、毎回の負担になる。発表会の当日にも、数分で状態を確かめたい。

これをスクリプトにし、deploy/a1-deploy.sh の最後から呼べるようにする。SRE の観点で、「デプロイしたら、動いていることを自動で確かめる」流れを作る。

## スコープ

### このissueでやること

- 外から確かめるスクリプト（公開 URL に対して。手元の Mac からも、A1 からも実行できる）
  - web の応答（200、タイトルなど）
  - WebSocket の接続と、session の受け取り
  - ルームの作成と退出（作った後に、必ず退出して、台帳に残さない）
  - ping が届くこと（約20秒待つ。短縮の指定も可能にする）
  - 素材配信（NEXT_PUBLIC_ASSET_BASE_URL が設定されているときだけ）: manifest の取得、CORS のヘッダ、キャッシュのヘッダ。2回目の取得でキャッシュが効いていること
  - 失敗した項目を一覧で出し、終了コードで成功・失敗を返す
- A1 の中で確かめる部分
  - コンテナ（rondo-app、rondo-ws、rondo-assets）が起動していること
  - 直近のログに、エラーが連続していないこと
- deploy/a1-deploy.sh の最後で、`--verify`（または既定で）呼べるようにする。失敗したときは、戻し方（docs/deploy.md）を表示する
- 実行結果を、日付つきで短く残す（標準出力でよい）

### このissueでやらないこと

- 継続的な監視（Prometheus の blackbox exporter など）。必要になったら、別 issue にする
- 負荷や長時間の試験（issue-51）
- ブラウザを使った確認（issue-48）

## 設計方針

- 確認は、利用者に影響しない操作だけにする（作ったルームは、必ず退出する）
- 秘密の値（env ファイルの内容）を、出力に出さない
- 確認の対象の URL は、引数または env ファイル（リポジトリの外）から受け取る
- 判定は項目ごとに独立させ、1つ失敗しても残りを続ける
- 一時的な失敗（起動直後など）に備え、再試行の回数と間隔を、設定で変えられるようにする

## 受け入れ条件

- 全項目が通ったときに終了コード 0、1つでも失敗したときに 0 以外で、失敗した項目が分かる
- 作ったルームが、確認の後にルーム一覧に残らない
- 素材配信を設定していない環境では、素材の項目を飛ばし、その旨を表示する
- シェルスクリプトを使う部分は、ShellCheck が通る
- deploy/a1-deploy.sh から呼べる
- `make verify` が通る

## 段階

1. docs/deploy.md の手作業の確認項目を一覧にする
2. 外から確かめるスクリプトを、項目ごとに作る
3. A1 の中の確認を作る
4. deploy/a1-deploy.sh へ組み込む
5. 手順と、失敗したときの見方を docs/deploy.md に追記する
