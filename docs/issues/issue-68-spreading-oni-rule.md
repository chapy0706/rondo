# issue-68: 増え鬼ルール（見つかった人が、鬼になる）

## 背景

本家のゲームで、ベーシックモードより人気があるのが、増え鬼である。鬼に見つかった人は、脱落せず、鬼の仲間になって、残りの隠れ側を探す。鬼がどんどん増え、隠れ側は減っていく。最後の 1 人が、時間まで逃げ切ったときの気持ちよさ（8 人中 7 人が鬼になっても、逃げ切った）が、このルールの見せ場になる。

いまのゲームは、鬼が 1 人で、見つかった人は、観戦（鬼の視点）に回る（issue-28）。本 issue では、ルール「増え鬼」を足し、ルーム作成の設定で、ベーシックと選べるようにする。あわせて、逃げ切りを称える「トロフィー」を、結果画面に出す。

優先度は、必須の作業（A1 への載せ換え、実機の確認など）と、issue-66（最大 8 人）の後。ゲームの中心の仕組み（鬼が 1 人であること）に触れる大きな変更なので、実装の前に、提案で止まる。

## スコープ

### このissueでやること

- ルール「増え鬼」（ルーム作成の設定。既定は、いまのベーシック）
  - 鬼に見つかった人は、鬼になる（観戦に回らない）。見つかった場所で、鬼として動き出す（短い待ち時間（定数。例: 3 秒）のあとに動けるようにするかは、提案して確認する）
  - 鬼は、増えていく。隠れ側が 0 人になったら、鬼の勝ち。探索の時間が終わったとき、隠れ側が 1 人でも残っていれば、残った人の勝ち（逃げ切り）
  - 鬼が増えても、隠れ側は、探索の間、動けない（ベーシックと同じ）。逃げ切りは、塗りと場所の工夫で決まる
  - 鬼の人数、隠れ側の人数が、全員の画面に出る
  - 鬼になった人の画面: 体が鬼の赤に変わり、「あなたも鬼になった」と出る。照準、撃つ、襖を開ける、の操作が使える
- 鬼が複数になることへの対応（サーバー、クライアント）
  - 鬼の位置と向きの通知を、複数の鬼を 1 通にまとめた形にする（待機ルームの同期と同じ、変わったときだけ、約 10 回/秒以下、補間つき）。契約の変更は、veryare の payload だけ
  - 射撃の判定（射程、見通し、間隔）は、鬼ごとに行う。同時に、同じ隠れ側を、複数の鬼が撃った場合は、サーバーが受け取った順で、最初の 1 つが有効（ADR 0014）
  - 鬼 CPU、隠れ CPU: 見つかった CPU の隠れ側は、鬼 CPU として動く（既存の鬼 CPU の仕組みを、鬼ごとに動かす）。計算の負荷を、シミュレーションと負荷試験で確かめる
- 結果とトロフィー
  - 結果: 勝敗、鬼になった順、逃げ切った人。ベーシックと同じ契約の形（game-ended の details に足す）
  - トロフィー（逃げ切りの称号）: 例として、「逃げ切り」（最後まで見つからなかった）、「孤高の逃げ切り」（鬼が 3 人以上いるときに、逃げ切った）、「奇跡の逃げ切り」（鬼が 7 人のときに、逃げ切った）。条件は、提案して確認する
  - 獲得の記録は、アカウントを持たないため（ADR 0015）、その端末に覚えさせる（localStorage。try/catch で囲む）。結果画面に、獲得したトロフィーを、目立つ演出で出し、設定の画面から、獲得の一覧を見られる
- ベーシックとの両立
  - ベーシックの動き（鬼が 1 人、見つかった人は観戦）は、変えない。既存のテストが、そのまま通ること
  - 増え鬼のとき、観戦（鬼の視点）に回る人は、いない
- ボット、E2E、シミュレーション
  - ボットのシナリオ: 増え鬼で、見つかった人が鬼になり、鬼の通知に載ること。隠れ側が 0 人になって終わる。時間切れで、1 人が逃げ切る
  - シミュレーションに、増え鬼を足し、異常が 0 件で、勝率が極端に偏らないことを確かめる（人数と探索の時間の組み合わせを、表にする）

### このissueでやらないこと

- ポイントといいね（issue-32）。増え鬼のあとに、組み込む。見逃しポイントの計算は、鬼が複数になったことを前提に、見直す
- アカウント、端末をまたぐ記録、ランキング
- 隠れ側が、探索の間に、動けるようにすること
- 観戦ルームでの増え鬼（issue-67 と、組み合わせは、別に検討）

## 設計方針

- ルールは、状態機械の、鬼の集合（1 人から、複数へ）という形に、まとめる。ベーシックは、「見つかった人は、鬼にならない」という設定の違いとして、同じ仕組みで表す。分岐を散らさない
- 鬼の通知は、1 通に、まとめて送る。鬼が増えても、通信量が、鬼の数に比例して増えないこと（測って報告する）
- 隠れ側の情報は、これまでどおり、探索の開始の一括配信で全員に届く（ADR 0035）。鬼になった人が、新しく得る情報は、ない（すでに届いていたもの）。この点を、テストと ADR に明記する
- 判定はすべて純粋関数で、テストを先に書く。受け入れの基準は ADR 0028 に従う
- ADR を新しく書く（番号は最新の次）。ADR 0035 の「鬼が 1 人」の前提と、ADR 0033 の終了の条件に、触れるため、書き換えず、置き換える

## 受け入れ条件

- 増え鬼で、見つかった人が、鬼になる。鬼の通知に載り、全員の画面で、赤い体が動く（ボットで確認）
- 隠れ側が 0 人になったら、鬼の勝ちで、答え合わせに進む。時間切れで、隠れ側が 1 人以上残れば、残った人の勝ち（テストで確認）
- ベーシックの動きと、既存のテストが、変更なしで通る
- 鬼が 7 人になっても、鬼の通知が、1 通で届き、通信量が目安に収まる（測定を報告）
- 同時に、複数の鬼が、同じ隠れ側を撃っても、最初の 1 つだけが有効で、二重に鬼にならない（テストで確認）
- 見つかった CPU の隠れ側が、鬼 CPU として動く。シミュレーションで、異常 0 件、勝率が極端に偏らない（表を報告）
- トロフィーが、条件を満たしたときだけ、結果画面に出る。localStorage が使えなくても、動く（テストで確認）
- 目視: 鬼が増えていく様子が、画面で分かる。逃げ切ったときの演出が、気持ちいい。スマホの縦画面で、8 人（鬼が 7 人）が動いても、重くない（実機）
- `make verify` が通る

## 段階

1. 鬼の集合の持たせ方（状態機械、通知、判定）、鬼になった瞬間の扱い、通信量の見積もり、トロフィーの条件、ベーシックとの両立、影響する範囲、見積もりを提案して、一度止まる
2. 鬼の集合と、増え鬼の判定を、テストを先に書いて実装する（サーバー）
3. 鬼の通知（複数まとめ）と、共有の見本を作る
4. 鬼 CPU の複数化、シミュレーション、ボットのシナリオを足す
5. クライアント（鬼の複数の描画と補間、鬼になった画面、人数の表示、結果とトロフィー）を実装する
6. 通信量と描画の重さを測り、目視で確かめる項目を、報告にまとめる
