# issue-51: 負荷・長時間・乱れた通信の試験

## 背景

発表会では、複数の来場者が同時に遊び、会場の通信は不安定になりうる。また、公開されているサービスなので、想定外の電文を送られても落ちないことが必要になる。上限（同時ルーム数3、定員5人）が実接続で効くことと、メモリが増え続けないことを、凍結（10/23）の前に確かめる。

issue-49 のボットの仕組みを使い、負荷・長時間・乱れた通信を自動で試す。

## スコープ

### このissueでやること

- 上限の試験
  - 同時に4つ目のルームを作ろうとして、断られること
  - 6人目の参加が、満員で断られること
  - 上限に達した状態から、退出や終了で空きが戻ること
- 同時接続の負荷
  - 3ルーム × 5人（15接続）を同時に動かし、フェーズ通知の遅延と、サーバーのメモリ・CPU を測る
  - 測定結果を、表にまとめる
- 長時間の放置
  - 待機ルームの接続を、1時間つなぎ続け、メモリの増え方と、切断が起きないこと（ハートビートが効くこと）を確かめる
  - 実行は、手元（ローカル）と、本番（Cloudflare 経由）の両方を、手順として書く
- 乱れた通信
  - ボットの接続をランダムに切り、猶予内に復帰する。猶予を過ぎたものは離脱になる
  - 他人の復帰トークンでは復帰できないこと
  - ルームとゲームの状態が、乱れたあとも矛盾しないこと（人数、フェーズ）
- 不正な入力
  - 壊れた JSON、未知の種別、極端に大きな電文、バイナリ、短時間の大量送信を送っても、サーバーが落ちず、他の接続に影響しないこと
  - 必要なら、電文の大きさの上限と、送信の頻度の上限を、サーバーに足す案を報告する（実装は、必要と判断した場合のみ。ゲームの既定の挙動は変えない）

### このissueでやらないこと

- ゲーム固有のロジックの変更
- 本番に対する、継続的な負荷の発生（短時間の確認に限る）
- 外部への攻撃的なテスト（自分の環境に限る）

## 設計方針

- 試験は、issue-49 のボットを土台にし、数・時間・乱れ方を引数で変えられるようにする
- 測定は、再現できる形で残す（条件と結果を表にする）
- 本番での試験は、手順を書くだけにして、実行の判断は人間が行う
- 落ちる、または状態が矛盾する問題が見つかったら、直す前に、再現する試験を先に書く
- 受け入れの基準は ADR 0028 に従う

## 受け入れ条件

- 上限の試験が、すべて通る
- 15接続の同時負荷で、遅延とメモリの測定結果が、表として docs にある
- 1時間の放置で、切断が起きず、メモリが増え続けないことを確かめた結果が、docs にある
- 乱れた通信と不正な入力で、サーバーが落ちない
- 見つかった問題が、直されているか、issue として起票されている
- `make verify` が通る

## 段階

1. issue-49 のボットを読み、試験の方式を提案する
2. 上限の試験を作る
3. 同時負荷の試験を作り、測定する
4. 乱れた通信と不正な入力の試験を作る
5. 長時間の放置の手順を作り、ローカルで実行する
6. 結果と、本番での手順を docs にまとめる
