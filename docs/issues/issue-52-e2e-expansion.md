# issue-52: E2E の拡張（スマホ表示・素材の失敗・状態の確認）

## 背景

issue-48 で、2タブの E2E（入口、同期、切断と復帰、ハートビート、接続の失敗）を作る。本 issue では、発表会の実際の条件（スマホの縦画面、タッチ操作、素材の読み込みの失敗）と、3D の状態の確認を足し、目視の回数を最小にする。

3D の canvas は、ピクセルの比較では不安定になりやすい。そのため、3D はテスト用に状態を読む口を用意し、数値で確かめる。

## スコープ

### このissueでやること

- スマホの端末設定での実行
  - Playwright の端末設定（縦画面のスマホ）で、シナリオを流す
  - WebKit（Safari と同じエンジン）でも流す。実機の iPhone の代わりではないことを、報告に書く
- タッチ操作
  - 2本パッドの入力を、タッチイベントで再現できるか確かめる（複数のタッチが要る場合は、CDP の Input.dispatchTouchEvent などを検討する）。難しい場合は、手動の項目として残し、理由を報告する
- 素材の失敗
  - 素材の配信を、404、壊れた glb、タイムアウト、manifest の欠落にして、画面が仮の表示で動き続けることを確かめる（リクエストの差し替えで再現する）
  - 素材が正常なとき、本素材に差し替わることも確かめる（疎通確認用の立方体の glb を使う）
- 3D の状態を読む口
  - テスト用の環境変数（既定は無効。本番では無効）で、ゲームの状態（フェーズ、自分の位置、襖の開閉、見えている隠れ側の数など）を、window 経由で読めるようにする
  - テストは、この口の値で確かめる（canvas のピクセルは比べない）
- 画面の見た目の比較
  - 3D ではない画面（選択画面、ロビー、失敗の表示、結果画面）を、スクリーンショットで比較し、前回との差分を見つける
  - 差分の許容の範囲を決める
- 目視でしか確かめられない項目の一覧を、docs に整理する（見る画面、見るべき点、頻度）

### このissueでやらないこと

- ゲームの判定ロジックの変更
- 実機の iPhone での確認の自動化
- 3D の見た目の自動比較
- 本番（Cloudflare 経由）の確認の自動化（issue-50）

## 設計方針

- テスト用の口は、環境変数が有効なときだけ作る。無効のときに、画面の挙動も、配信するファイルの大きさも変わらない
- 値の取得は、読み取り専用にする。テストから、ゲームの状態を書き換えない
- スクリーンショットの基準画像は、リポジトリに入れてよい（素材を含まない画面のみ）。素材（平屋、キャラクター）が映る画面の基準画像は入れない
- 待ち時間は、固定の秒数ではなく、状態を待つ

## 受け入れ条件

- スマホの縦画面の設定で、issue-48 の主要シナリオが通る
- WebKit で、主要シナリオが通る（通らない場合は、原因と対応の見通しが報告されている）
- 素材の失敗4種で、画面が止まらず、仮の表示で続く（テストで確認）
- テスト用の口が、環境変数なしでは存在しない（テストで確認）
- 3D ではない画面のスクリーンショット比較が動く
- 目視の項目の一覧が、docs にある
- `make verify` が通る

## 段階

1. issue-48 のテストと、画面の構成を読み、拡張の方式を提案する
2. 端末設定と WebKit の実行を足す
3. 素材の失敗のシナリオを足す
4. 状態を読む口を、テストを先に書いて実装する
5. タッチ操作の再現を試す
6. スクリーンショット比較を足す
7. 目視の項目の一覧を docs にまとめる
