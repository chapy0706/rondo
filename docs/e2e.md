# 実接続の起動と E2E スモーク（issue-48）

## 起動

```bash
make dev-all
```

- Gleam サーバー: `ws://localhost:3000/ws`
- web（Next.js の開発サーバー、実接続）: `http://localhost:3100`
- WebSocket の URL は `tools/dev-all.sh` が渡す。手で環境変数を付けなくてよい
- Ctrl-C で両方が止まる。片方が止まったときも、もう片方を止める

モックで動かすときは、これまでどおり `make dev`（`http://localhost:3000`）。

## E2E スモーク

初回だけ、Playwright のブラウザを取得する（ネットワークを使う）。

```bash
pnpm --filter @rondo/e2e exec playwright install chromium
```

```bash
make e2e          # シナリオ1〜4（約2〜3分）
make e2e/result   # シナリオ5（鬼選出から結果画面まで。約2分）
```

- `make dev-all` が動いていれば、それを使う。動いていなければ、同じポートで起動して、終わったら止める
- `make verify` には含めない（時間とブラウザに依存するため）
- 失敗したときの記録（trace）は `e2e/test-results/`、一覧は `e2e/playwright-report/`（どちらもコミットしない）

| シナリオ | 確かめること |
| --- | --- |
| 1 入口と同期 | 選択画面の「新しく遊ぶ」と「ルームに参加する」で同じルームに入り、円の色が赤 → 緑 → 青と、両方で揃って変わる |
| 2a 切断と復帰 | B を3秒だけ遮断して戻すと、同じルームに復帰し、同期が続く |
| 2b 猶予切れ | B を猶予（10秒）より長く遮断すると、A は1人に戻り（赤）、B に「前の接続に戻れませんでした」が出る |
| 3 ハートビート | ping が約20秒ごとに届き、そのたびに pong を返す |
| 4 接続の失敗 | 遮断したまま「新しく遊ぶ」を押すと、約10秒で「つながりません」が出る。戻して「もう一度」で入れる |
| ステージと襖の通知 | 入室すると、両方のタブにステージの通知と襖の通知が届く（WebSocket のフレームで見る / issue-29d） |
| 5 結果まで | 探索の開始で両方のタブの襖が全部閉じ（`data-open-doors` が 0）、鬼が襖の前まで歩いて開ける報告を送ると、両方で 1 になる。答え合わせで襖が全部開き、隠れていた B が両方のタブで点滅の対象になる（`data-blinking` が 1）。ペイントフェーズに B が自分の体（画面の中央）をタップして塗り、「塗り終わり」を押すと、ペイントの確定が一度だけ送られ、A には探索の開始の一括配信で初めて届く（issue-25）。結果画面まで進み、隠れ側が1位・鬼が2位で出る。「退出する」でロビーへ戻る |

### テストの作りの注意

- veryare の移動は画面のジョイスティック（タッチ）なので、「中央の円に触れる」は、そのタブの接続からサーバーへ移動の電文を送って代える（`e2e/tests/wsLink.ts`）。判定はサーバーがいつもどおり行う
- 通信の遮断は、そのタブの WebSocket の経路で行う。サーバー側の接続を切り、ページ側は開いたまま黙らせる（応答のない回線と同じ見え方）。ブラウザ全体のオフラインの切り替えは、開いている WebSocket に効かないことがあるため使わない
- 待ち時間は秒数ではなく、画面の状態（`data-testid` と `data-color`）を待つ

## 手作業で確かめる項目（自動化していないもの）

- 本番（Cloudflare 経由）で、無操作の待機ルームが2〜3分維持される（手順は issue-41 の報告）
- スマホの実機（画面ロック、アプリの切り替え、着信）での切断と復帰（ADR 0013）
- 実際の回線の断（Wi-Fi を切る、機内モード）で、約50秒後に再接続または「つながりません」に移る（ブラウザの無通信の検知）
- ジョイスティックでの移動と、中央の円に自分で入ったときの立候補
- 見た目（3D の描画、円の色、結果画面のレイアウト、スマホの縦画面）
- リロードでの復帰（sessionStorage の復帰先。E2E は1つのページの中の切断だけを扱う）
- 返事の前に画面を離れたときの取り残し（ルームの人数が戻ること / issue-47）
- 3つ以上のタブ（定員5人、同時ルーム数3）
- `make bots` で、全シナリオが通る（サーバーの起動を伴うので `make verify` に含めない。「全員発見」は、見通しが有効でも当たる場所に隠れ側がいる / issue-29a・29b・49）

### veryare のステージ（issue-29c）

2つのタブ（A を鬼、B を隠れ側）で、`make dev-all` の画面を見る。

- 床・壁・襖の見た目: 部屋（畳の色・押し入れの暗い色）と廊下（板の色）が見分けられる。壁（灰茶）と閉じた襖（明るい生成り色の板に、濃い木の鴨居と柱）が見分けられる。いつも閉じている戸は壁と同じに見え、いつも開いている戸は開口になっている
- 玄関から始まる: B は準備移動の開始で、A は探索の開始で、玄関に立つ
- 動きの手触り: 壁と閉じた襖で止まり、壁に沿って滑る。角や壁沿いで引っかからず、位置の合わせ直し（瞬間移動）が目立たない
- 襖を開ける: 閉じた襖の 1.5 m 以内で「襖を開ける」が出て、押すと A・B の両方のタブで板が消え、通れるようになる。押す前には通れない
- 隠れ側の体の色: ペイント前は仮の色（白に近い薄紫）のまま。床の色との溶け込みは、issue-25 の後に確かめる
- スマホの縦画面: 移動パッド・撃つボタン・襖を開けるボタンが押しやすく、描画が重くない（最も大きい骨格でも、箱は色ごとの十数回の描画にまとめている）
- カメラ: カメラはキャラクターの後ろ 2.6 m にあり、壁の高さ（2.4 m）より低い。狭い廊下で横を向くと、壁が手前に来て自分が隠れることがある（ADR 0034 で衝突の補正はしない）

### マイルストーン1の通し（issue-29d）

鬼選出 → 準備移動 → 探索（撃つ）→ 答え合わせ → 結果が、2〜3タブで通ることを見る。ペイントは仮の色のまま、観戦はいまの挙動のまま。`make dev-all` の画面を、2つ（または3つ）の別のブラウザのウィンドウ（シークレットウィンドウを含む）で開く。スマホの縦画面でも1回通す。

1. 鬼選出: A が「新しく遊ぶ」、B（と C）が「ルームに参加する」で入る。円が緑になったら、A が中央の円へ歩いて入る。円が青になり、10 秒後に A が鬼になる
2. 準備移動（20 秒）: B（と C）が玄関に現れる。襖は全部開いている。玄関から遠い部屋まで歩き、20 秒のうちに着ける（歩く速さ 4.5 m/秒の手触り）。B と C は別の場所に隠れる（重なると失格）
3. ペイント（20 秒）: 隠れ側は動けない。鬼は待機ルームにいる
4. 探索（40 秒）: A が玄関に現れる。襖は全部閉じている。A が襖に近づくと「襖を開ける」が出て、押すと全員のタブで開く。閉じた襖越し・壁越しに撃っても当たらない。見通せる隠れ側を照準に重ねて撃つと「見つけた！」が出て、撃たれた人は観戦になる
5. 答え合わせ（20 秒）: 襖が全部開いて見える。隠れていた全員（見つかった人も、逃げ切った人も）が、全員のタブで1秒ごとに赤く点滅する。自分が隠れ側なら、自分の体も点滅する。端末で「視差効果を減らす」を入れている人には、点滅せず赤く光ったままに見える
6. 結果: 全員のタブが結果画面に移り、順位と状態（逃げ切り・発見・失格・離脱）が出る。「退出する」でロビーへ戻れる

失敗したときは、どの段で止まったか、そのときのブラウザの開発者ツールのコンソールの赤いエラーの行（`Uncaught` から、スタックの最初の5行まで）を控える。

### 平屋のステージ（issue-46）

平屋は、見通しの一般化（issue-45）が通るまで、ロビーの選択肢に出さない（`apps/web/src/games/veryare/manifest.ts` の `HIRAYA_READY`）。手で確かめるときだけ、開発用の環境変数 `NEXT_PUBLIC_VERYARE_HIRAYA=1` で選択肢を出す（本番のビルドには渡さない）。

配るフォルダ `assets-src/delivery/`（manifest.json と、版付きのパスの glb）が無ければ、先に作る（素材はコミットしない。`docs/assets.md` の「manifest.json を作る」と同じ）。

```bash
# 平屋のゲーム用 glb（meshopt で圧縮した 6 本。issue-55）が無ければ作る
node tools/build_house.mjs assets-src/house/hiraya-fbx.glb assets-src/converted/house-fbx-meshopt
# 版付きのパスに並べる（疎通の確認用の立方体も残すときは v1/test も）
mkdir -p assets-src/delivery/v2/house assets-src/delivery/v1/test
cp assets-src/converted/house-fbx-meshopt/*.glb assets-src/delivery/v2/house/
cp assets-src/test/v1/test/*.glb assets-src/delivery/v1/test/
# manifest.json を作る（key・quality・version・path・bytes は、ファイルから計算する）
node tools/make_manifest.mjs assets-src/delivery
```

起動の順番（この順で行う。`tools/serve-assets.mjs` は Docker なしで手元から素材を配る道具で、Node の標準モジュールだけで動き、127.0.0.1 だけで待ち受ける）:

1. 素材の配信を先に起動する

   ```bash
   node tools/serve-assets.mjs                      # assets-src/delivery を http://127.0.0.1:8081 で配る
   ```

2. 別のターミナルで、変数を付けて web とサーバーを起動する。`NEXT_PUBLIC_*` は起動したときに埋め込まれるので、変数を変えたら `make dev-all` を止めて起動し直す

   ```bash
   NEXT_PUBLIC_VERYARE_HIRAYA=1 NEXT_PUBLIC_ASSET_BASE_URL=http://localhost:8081 make dev-all
   ```

3. ブラウザの開発者ツールを、ページを開く前に開く（Console と Network。Network の「Preserve log」に印を付ける）。先読みはロビーを開いた瞬間に始まり、Network は開いている間の要求しか記録しないため
4. アドレス欄に `http://localhost:3100/lobby/veryare` を入れて開く（`127.0.0.1` ではなく `localhost`）。serve-assets が許可するオリジンは既定で `http://localhost:3100` だけで、`http://127.0.0.1:3100` からの読み込みは CORS で止まる（curl は CORS を見ないので、curl では返ってくる）。`127.0.0.1` で開くなら、1 を `node tools/serve-assets.mjs --origin http://127.0.0.1:3100` で起動する

- `serve-assets.mjs` の引数: `--dir`（配るフォルダ。既定 `assets-src/delivery`）、`--origin`（CORS で許可するオリジン。既定 `http://localhost:3100`。本番の `ASSET_ALLOWED_ORIGIN` と同じく、この1つを返す）、`--port`（既定 8081）
- 本番の rondo-assets と同じく、配るのは `/manifest.json`（キャッシュ 60 秒）と `/v<数字>/…/*.glb`（1年・immutable）だけ。GET と HEAD だけで、ディレクトリの一覧は出さない。要求ごとに「方法 パス 状態」の1行を出す
- 本番と同じ nginx で確かめたいときは、これまでどおり Docker でも起こせる（`docker build -t rondo-assets deploy/assets` の後、`docker run --rm -p 8081:3000 -e ASSET_ALLOWED_ORIGIN=http://localhost:3100 -v "$PWD/assets-src/delivery:/srv/assets:ro" rondo-assets`）
- `NEXT_PUBLIC_VERYARE_HIRAYA=1` のときは、ロビーを開いた時点で平屋の glb の先読みが始まる（ロビーを離れても止めない）。Network に、ロビーの画面で `hiraya-indoor-512.glb` などが出る
- 屋根の切り替えボタンは開発用だけ。`NEXT_PUBLIC_VERYARE_HIRAYA=1` のときか、ゲームの画面の URL に `?roof=1` を付けたときだけ出る（来場者の画面には出さない。屋根は隠したまま）
- manifest.json の取得に失敗したときは、5 秒たったあとの次の読み込みで取り直す（失敗を覚え続けない）。serve-assets を後から起動したときは、5 秒以上待ってからロビーを開き直す（またはページを読み直す）

ログの見方（Console）:

| 印 | 出るとき | 読み方 |
| --- | --- | --- |
| `[veryare-assets]` | 開発中だけ（`NEXT_PUBLIC_VERYARE_HIRAYA=1` か、URL に `?roof=1`） | 素材の流れ。上から順に「ロビー: 平屋の glb の先読みを始めた」→「manifest.json: 取得できた」→「hiraya-indoor・hiraya-outdoor・hiraya-roof: 読めた」→「対戦: 先読みの結果を、差し替え口に使う」→「待機ルーム: 平屋の glb に差し替えた」→「ステージ: 平屋の glb で表示している」と出れば、正しく流れている。途中で止まった行と、その理由を見る |
| `[assets]` | 素材の読み込みに失敗したとき（本番でも出る） | 失敗の理由と URL（例: `manifest-unavailable: http://localhost:8081/manifest.json を取得できない（TypeError: Failed to fetch）`）。CORS で止まったときは、ブラウザ自身の CORS のエラーの行も並んで出る |
| `[lobby]` | 開発中だけ、ロビーの先読みを始められなかったとき | 先読みの部品の読み込みの失敗。通常は出ない |

`[veryare-assets]` の行が1つも出ないとき、または途中で止まるときに、まず疑う点:

- 変数: 「ロビー: 先読みしない（HIRAYA_ENABLED が false…）」なら、`NEXT_PUBLIC_VERYARE_HIRAYA=1` が web に届いていない。行が1つも出ないときも同じ。変数を付けて `make dev-all` を起動し直す（ロビーにステージの選択肢が出ていれば、変数は届いている）
- 素材の URL: 「manifest.json: 取りに行かない（NEXT_PUBLIC_ASSET_BASE_URL が未設定）」なら、`NEXT_PUBLIC_ASSET_BASE_URL` が届いていない
- オリジン: 「manifest.json: 取得できない」と、ブラウザの CORS のエラーが出たら、アドレスが `http://localhost:3100` か、serve-assets の `--origin` と合っているかを見る
- serve-assets の起動順: serve-assets を後から起動したなら、5 秒以上待ってからロビーを開き直す。serve-assets のターミナルに `GET /manifest.json 200` が出ているかも見る
- ルームが平屋か: 「ステージ: 箱のまま（平屋の通知ではない（ランダム間取り））」なら、ロビーでステージを「平屋」にせずに作った（または、選択画面の「新しく遊ぶ」から作った。こちらは、いつもランダム間取り）
- 間に合わなかった: 「ステージ: 箱のまま（待機ルームの間に読み終わらなかった…）」なら、読み込みがステージに入るまでに終わらなかった。その回は箱のままで、次の対戦で使われる

平屋のルームの作り方: ロビー（`http://localhost:3100/lobby/veryare`。選択画面の「ルームに参加する」からも行ける）で、ステージを「平屋」、CPU を「なし」にして作る。選択画面の「新しく遊ぶ」は設定を送らずに作るので、いつもランダム間取りになる。送る設定の形は `{ stage: 1, cpu: 0 }`（create-room の settings。`stage` は 0 = ランダム間取り、1 = 平屋）。平屋と CPU の組み合わせは、issue-45 までサーバーが拒む。ボットで通すときは `make bots ARGS="--only 平屋"`。

素材の無い表示で確かめるときは、`NEXT_PUBLIC_ASSET_BASE_URL` を付けずに起動する（箱の表示になる）。

2つのタブ（A を鬼、B を隠れ側）で見る。スマホの縦画面でも1回通す。

- 見た目: 待機ルームの間に読めていれば、ステージに入ったときに平屋が見える（間に合わなければ、その回は箱のまま）。屋根と天井は隠れている。開発用の指定があるときだけ、「屋根を表示する」で出し、「屋根を隠す」で隠せる。指定が無いとき（本番の既定）は、ボタンが出ない
- 足もと: 平屋の glb を表示しているとき、体（自分・鬼・隠れ側・CPU）が床にめり込まず、床の上に立つ（畳 0.6 m、土間 0.4 m、縁側 0.55 m、床の間 0.62〜0.72 m、トイレの段 0.8 m）。玄関から廊下へ上がるときなどの段差で、足もとが跳ねずに、短い時間（約 0.12 秒）で寄る。カメラも体の高さについて行く。箱の表示のときは、これまでどおり床が 0
- 判定の壁と見た目の壁: 壁沿いに歩いて、見た目の壁と止まる位置のずれが小さい（判定は 0.3 m の格子で、壁の中心線から最大 0.125 m ずれる）。家具は通り抜けられる（当たりを持たない）
- 襖: 探索の開始で全部閉じ、閉じた襖の前で止まる。「襖を開ける」で、その襖の板が全部消え（枠の鴨居と柱は残る）、全員のタブで同じ襖が開く。開いた襖は、見た目どおり全幅が通れる。準備移動の間と答え合わせでは、全部開いている
- カメラ（ADR 0043）: 壁際や部屋の隅で視点を回しても、カメラが壁の向こう（隣の部屋）に出ず、近づいたぶん上から見下ろす。開いた襖や戸口を通るときも、カメラは体のいる部屋の中にとどまる。離れるときは、なめらかに戻る（跳ねない）。ペイント画面と待機ルームでは、これまでどおり
- 狙い（鬼）: 画面をタップ（短く、あまり動かさない）すると、そこに黄色い目印の球が出る。隠れ側の体をタップすると、その隠れ側が黄色く光る。「撃つ」で、目印の所にいる隠れ側を申告する（いなければ外れ）。タップしていなければ、これまでどおり画面の中央を狙う。移動パッドを動かしながら、別の指でタップしても狙える。平屋でも、見える相手には当たる（壁越し・閉じた襖越しは外れ、開けた襖越しは当たる / issue-45）。外れたときは、手元の推定で理由（「外れ: 遠すぎます（8 m まで）」「外れ: 襖が閉まっています」「外れ: 壁の向こうです」「外れ: 狙った所に、隠れている人がいません」）が 1.5 秒出る（表示だけで、判定はサーバー）。開発中は Console に `[veryare-shoot] 申告を送った: target=…` と、0.5 秒後に `[veryare-shoot] 結果: target=…・推定=…・隠れている … → …` が出る
- カメラの定数（開発中だけ）: `NEXT_PUBLIC_VERYARE_HIRAYA=1` のときか、URL に `?roof=1` を付けたとき、URL の指定でカメラの定数を変えられる（例: `?roof=1&camPitchMax=0.45&camLookAhead=1.5`）。名前は `camDistance`（距離）・`camPitch`（既定の角度）・`camPitchMax`（近づいたときの角度の上限。既定 0.45）・`camMargin`（壁から離す距離）・`camSettle`（離れるときに戻る時間）・`camMinHeight`（高さの下限）・`camLookAhead`（近づいたとき、見る点を前へずらす距離。既定 1.0、0 でずらさない）。範囲の外の値は無視する
- カメラの高さの記録（開発中だけ）: 同じ合図のとき、Console に 1 秒ごとに `[veryare-camera] 床 0.60 m・カメラは床から 1.85 m（世界の y 2.45）・水平の距離 2.44 m・見下ろす角度 13°` のような行が出る
- カメラが壁に近づいたとき: カメラは部屋の外に出ず、見る点が前へずれるので、真上から足もとを見下ろさない（見下ろす角度は、開けた所で約 13°。カメラの高さの上限 1.85 m にかかるため）
- カメラのめり込み（平屋の glb を表示しているとき）: 壁際・部屋の隅・タンスや冷蔵庫や食器棚のそばで視点を回しても、カメラが壁や家具の中に入らず、壁の中（断面）が映らない。背の高い家具が体とカメラの間に来ると、カメラは家具の手前で止まる。低い家具（座卓・ちゃぶ台など）では止まらない。家具の箱は、家具の glb（`hiraya-furniture`）から読む。開発中は Console に `[veryare-assets] 家具の箱: 142 個（カメラの守りに使う）` と出る（読めなければ「読めない（地図の守りだけ）」）。体が家具に入り込んだ場所（流し台と壁の隙間、床の間の棚の下など）では、向きによっては家具が体を隠す（めり込みはしない）
- 自動の全探索（手元）: `node tools/check_camera_hiraya.mjs`。めり込みが 0 件なら終了コード 0。ブラウザの E2E（サンプル）: `pnpm --filter @rondo/e2e e2e:hiraya`（`make dev-all` を止めてから。素材の配信と web をテスト用の口つきで起動する。`e2e/playwright.hiraya.config.ts`）
- テスト用の口: `NEXT_PUBLIC_RONDO_TEST_HOOKS=1` のときだけ、`window.__rondoTest.veryare`（`ready()`・`camera()`・`furniture()`・`probeCamera(x, z, yaw)`）ができる。本番のビルドは、この変数を渡さない
- 自分の体の半透明: カメラが体に近づく（水平の距離が 1.0 m 未満）ほど、自分の体（鬼本人の体を含む）が半透明になり、0.3 m 以下で最も薄くなる
- 移動パッドと視点パッド: 触ると、指の所につまみ（薄い丸）が付いていく。離すと（パッドの外で離しても）0.1 秒で中心へ戻り、動き・回転が止まる。中心のわずかな傾き（半径の 15% 未満）では動かない。片方のパッドを押したまま、もう片方のパッドや「撃つ」を押しても、先のパッドの向きは変わらない。押したまま、別のタブに切り替える・ウィンドウの外をクリックする・捕まって観戦に変わる、のどれでも、戻ったときに勝手に動かない
- 鬼の体: 鬼本人の画面では、赤い体が手元で動き、後ろから赤い円柱がついてこない。隠れ側・観戦者の画面では、鬼の赤い体がなめらかに動く（人間の鬼は約 0.1 秒、鬼 CPU は約 0.5 秒遅れて見える）
- 片開き戸（風呂-洗面所、洗面所-東の廊下、トイレ-東の廊下）: 開いた姿で置かれ、通れる。開く向き（どちらの部屋の側へ開くか）がおかしければ、`hiraya.ts` の `HINGED_SWING` を直す
- 縁側から庭へは出られない。玄関の戸と勝手口からは外へ出られない
- 射撃: 平屋でも、見える相手には当たる。壁越し・閉じた襖越しは外れる（ボットでは `make bots ARGS="--only 平屋の壁越し"`）
- 読み込み時間: 開発者ツールの Network で、`hiraya-indoor-512.glb` の取得の時間を控える。スマホでは、待機ルームの間（鬼選出の 10 秒と準備移動まで）に読み終わるか

### veryare のペイント（issue-25）

隠れ側のタブ（B）と鬼のタブ（A）で見る。スマホの縦画面でも1回通す。

- ペイントフェーズに入ると、B の画面にペイントの道具（色・グラデーション・スポイト・ブラシ・1つ戻す・全部消す・塗り終わり）が出る。A には出ない
- B が自分の体をなぞると、塗った内容がその場で体に映る。視点パッドで体の周りを回り、背中も塗れる。継ぎ目（体の真後ろ）をまたいで塗っても切れない
- 「ここの色」がいまいる部屋の床の色と同じに見える。スポイトで床・壁をタップすると、その色になる。体をタップすると、塗った色を拾う
- 平屋の glb を表示しているとき: スポイトで畳をタップすると、畳の見た目の色（黄緑がかった色）になる（黒にならない）。拾うのは、見えている一番手前の面の、素材の色とテクスチャの色（ライトの当たり方は含めない）。屋根・天井（隠れているとき）・ガラスは拾わない。「ここの色」も、足もとの床の見た目の色になる

キャラクターの素材（issue-56）: 配信するフォルダに `character-body`・`character-poses` を置いておく（`docs/assets.md` の「配信する形にする」）。素材が読めないときは、仮のカプセル（高さ 1.6 m）のまま最後まで遊べる。

- 体: 素材が読めたとき、待機ルームの間に、自分・ほかの隠れ側・CPU・鬼の体が人型になる（鬼は赤い人型で、立ち姿のまま。正面の印が付く）。開発中は Console に `[veryare-assets] キャラクター: 素材の体に差し替えた` と出る
- 体の高さ: 素材の体も仮のカプセルも 1.6 m。目の高さ（カメラが見る点）は 1.28 m、カメラは足もとから 1.85 m より高くならない
- ポーズボタン: ペイント画面にだけ「ポーズ（表示名）」のボタンが出る（仮のカプセルのときは出ない）。押すたびに、いまと違うポーズにすぐ変わる。足もとと位置の補正は、約 0.12 秒でなめらかに寄る
- ペイントとポーズ: ポーズをとったまま、体をタップして塗れる。ポーズを変えても、塗った模様は体の同じ部分について行く。胴と関節の継ぎ目で模様が切れない
- 確定: ポーズボタンを押していれば、何も塗っていなくても「塗り終わり」を押せる（終わりの 2 秒前にも自動で送る）。ペイントフェーズの間は、ほかの人の画面にポーズは出ない
- 鬼の画面: 探索の開始に、隠れ側が塗った色と選んだポーズで見える。CPU は立つ・しゃがむ・寝るのどれか。答え合わせの赤い点滅が、人型の体の上に重なる
- 床: 寝る・座る・跳ぶポーズでも、体が床に沈まず、浮かない
- 残り 2 秒になると「あと2秒で確定（もう塗れません）」が出て、それ以上塗れない。何も塗っていなければ何も送られない
- 探索が始まると、A の画面で B の体が塗った色で見える。「ここの色」で塗った体が、床の上で見分けにくい（溶け込む遊びになっている）
- 答え合わせの赤い点滅が、塗った体の上に重なって見える
- 隠れ側4人分（CPU を含む）の体を描いても、描画が重くならない

### 既知の抜け（veryare のペイント / issue-25）

- ペイントフェーズの間にリロード・再接続すると、描いていたペイントは消える。ペイントは終わりの 2 秒前（か「塗り終わり」）まで手元にしかなく、サーバーにもどこにも残らない（ADR 0025）。探索中・答え合わせ中に入り直したときは、確定したペイントが一括配信の送り直しで戻る
- 鬼 CPU は、人間の隠れ側のペイントを見ず、未塗装として扱う（`docs/schedule.md` の既知の抜け）

### 既知の抜け（veryare の位置の合わせ方 / issue-29c）

クライアントは、サーバーの移動の規則を手元で動かし、報告のたびにサーバーの結果を再現して、1 cm 以上ずれたら手元を合わせる（`apps/web/src/games/veryare/stage.ts` の `mirrorMove`・`reconcile`）。サーバーは自分の位置を送り返さないので、次の場合のずれは直らない。

- 報告を送ってからサーバーが受け取るまでの間に、襖の状態が変わった場合（閉じる前の報告がサーバーで閉じた後に届く、など）。手元は通り抜け、サーバーは襖の手前で止まる。以後の報告は、サーバーの位置から動かされるので、壁の向こうへは進めず、手元とサーバーで位置が食い違ったままになる
- リロード・再接続のあと。手元は玄関（または待機ルームの初期位置）から始め直すが、サーバーは前の位置を持っている。同じ地図が届き直しても、立ち直さない。ただし、探索中・答え合わせ中は、入り直した人へ隠れ側の通知が送り直される（issue-29d）ので、隠れ側の自分の体は隠れた場所へ戻り、答え合わせの点滅も出る。準備移動中の隠れ側と、探索中の鬼は戻らない
