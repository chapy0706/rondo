# ADR 0044: 待機ルームを半径 3.5 m に広げ、待機中のメンバーをサーバーから同期する

- ステータス: 提案（下書き）
- 日付: 2026-10-13
- 関連: ADR 0024（フェーズ制進行と待機ルーム）の「床面積の目安は 8 畳相当（半径約 2 m）」と、理由の「新しい同期の仕組みなしで」を置き換える。ADR 0007（単一の接続の多重化）、ADR 0009（契約は TypeScript が正）、ADR 0021（限定配信）、ADR 0025（ペイントの同期）、ADR 0035（性善説）。本 ADR は ADR 0024 を書き換えない

## 文脈

ADR 0024 は、待機ルームを半径約 2 m の円柱とし、鬼を退屈させない工夫を「新しい同期の仕組みなしで」実現するとした。待機ルームでは、自分の体しか見えず、同じルームの他の人がどこで何をしているかが分からない。

発表会では、複数の来場者が同じルームに入る。待機ルームで他の人の体が見え、動き、ポーズをとっていると、「みんなで遊んでいる」感じが出る（issue-59）。一方、半径 2 m では、5 人が席の輪（半径 1.3 m）に立つと、隣の席との間が約 1.5 m しかない。また、TPS カメラ（体から約 2.6 m 後ろ）が壁の外に出やすく、他の人の体が画面に収まりにくい。

## 決定

**広さ**: 待機ルームの半径を 3.5 m（直径 7 m、約 38 m²）とする。席の輪（入室したときの初期位置）の半径は 2.0 m とする。鬼希望エリアの半径（0.6 m）は変えない。値はサーバー（game.gleam の waiting_room_radius・waiting_ring_radius）とクライアント（rules.ts の WAITING_ROOM_RADIUS・WAITING_ROOM_SPAWN）で同じにし、共有の見本（veryare-movement.json の円の丸めの例）を両方のテストで通して確かめる。

**メンバーの同期**: 鬼選出フェーズの間だけ、サーバーが、待機ルームにいる人間の参加者全員の位置・向き・待機ポーズを 1 通（veryare の payload `members`）にまとめ、ルームの全員へ送る。

- 位置は、サーバーが円に丸めた後の値を正として送る。クライアントが自己申告した位置を、そのまま配らない
- 送る間隔は 150 ms とする。変わったとき（位置・向き・ポーズ）にタイマーを張り、起きたときに、最後に送った内容と違えば送る。誰も動かない・変わらないときは送らない
- 位置は小数第 2 位、向きは 0.05 rad 単位に丸めてから比べる（細かい揺れで送らない）
- フェーズが変わったら（step が進んだら）送らない。ステージの位置は、この通知に載らない
- 途中参加・再接続の人には、いまの様子を本人宛てに送る（既存の送り直しの仕組み）
- 名前は載せない。クライアントは参加者の一覧（room-joined / player-joined）から引く
- CPU は待機ルームに描かない（通知に載せない）。CPU はステージが始まってから現れる

**待機ポーズ**: 待機ルームでポーズを変えられるようにする（veryare の payload `waiting-pose`）。待機ポーズは同期する飾りの状態で、ゲームの隠れ側のポーズとは別に持つ（サーバーもクライアントも別の変数）。鬼選出が済んだら空にする。サーバーは、鬼選出中だけ、決まった一覧（pose.gleam の識別子）にあるものだけを受け付け、同じ人の変更は 0.3 秒あける。

## 理由

- 半径 3.5 m・席の輪 2.0 m では、隣の席との間が約 2.35 m、席から鬼希望エリアの縁まで約 1.4 m、壁まで約 1.5 m になる。5 人が並んでも、互いの全身が見え、エリアへは 2〜3 歩で行ける。4 m 以上にすると、スマホの縦画面で、エリアと他の人を一度に見にくくなる
- 待機ルームは、ゲームの判定に関わらない場（鬼選出のエリアへの接触を除く）であり、メンバーの位置を全員に見せても、隠れ側の位置の秘密（ADR 0025・0026）は損なわない。ステージに移ったら同期を止めることで、この境を保つ
- 150 ms の間隔なら、1 ルーム 5 人が動き続けても、送る通数は 5 宛先 × 約 6.7 回 = 約 33 通/秒に収まる（目安の 50 通/秒以下）。100 ms では目安の上限ちょうどになり、フェーズの通知などが加わると超える
- 待機ポーズを隠れ側のポーズと分けることで、待機で見えたポーズが、そのまま隠れ側のポーズとして鬼に知られることを防ぐ
- 名前を通知に載せないことで、1 通を小さく保つ。参加者の一覧は、すでにクライアントが持っている

## 検討した代替案

- クライアントが自分の位置を、他のクライアントへ直接配る案。サーバーの丸めを経ない値が届き、位置の正が二つになるため採用しない
- 動くたびにすぐ送る案（鬼の観戦の配信と同じ）。5 人が同時に動くと、通数が人数の二乗で増えるため、まとめて間隔を空ける形にした
- 半径 4 m・席の輪 2.4 m の案。エリアが遠くなり、画面に収まりにくいため採用しない

## 結果

- game.gleam の waiting_room_radius を 3.5、waiting_ring_radius を 2.0 にする。rules.ts の WAITING_ROOM_RADIUS を 3.5、WAITING_ROOM_SPAWN を (0, 2.0) にする
- 契約（packages/contracts/src/veryare.ts）に VeryareMembersNotice と VeryareWaitingPoseEvent を足し、共有の見本を TS と Gleam の両方で読む。外側の電文は変えない
- Game に waiting_poses を持たせ、鬼選出が済んだら空にする。送る制御（最後に送った内容・タイマーを張っているか）は Game の中で、判定の状態とは別の項目として持つ
- クライアントは、他のメンバーの体を、届いた通知の補間で描く（issue-59 の後半）。クライアントのフェーズが鬼選出でなければ、届いた members を捨てる
- issue-51 の負荷試験に、待機の同期を対象として加える
