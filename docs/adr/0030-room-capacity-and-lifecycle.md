# ADR 0030: veryare のルーム定員・参加導線・永続性

- ステータス: 受理
- 日付: 2026-09-29

## 文脈

rondo 全体のルーム参加は「一覧から参加、なければ新規作成」（ADR 0016）と定めている。veryare では、鬼1人という制約（ADR 0024）や、発表会での運用（同時に遊ぶグループ数、部屋を立てる人が限られること）を踏まえて、定員・同時ルーム数・ルームの寿命を具体的に定める必要がある。

## 決定

**定員**: 1ルームの最大人数は5人（鬼1人 + 隠れ側最大4人）とする。

**同時ルーム数**: veryare の同時アクティブルームは最大3つとする。4つ目のルーム作成は、既存のいずれかが終了するまでできない。

**ルーム一覧**: 現在アクティブな veryare のルーム一覧（最大3件）から選んで参加する（ADR 0016 の一般ルールに、件数上限を追加する形）。探索フェーズの時間設定（ADR 0024）はルーム一覧の時点では表示しない。

**ルームの寿命**: ルームを作成したプレイヤー（ホスト）が退出しても、ルーム自体は存続し、他のプレイヤーがそのまま使い続けられる。ルームは room_actor というサーバー側のプロセスとして存在しており（ADR 0006）、特定の接続に寿命が紐づく設計ではないため、この挙動は既存の仕組みと自然に両立する。

## 理由

- 発表会では最大3グループが同時に遊ぶ想定であり、同時ルーム数の上限をこれに合わせておくことで、際限なくルームが乱立することを防ぐ
- 1ルーム5人（鬼1・隠れ4）は、鬼1人固定（ADR 0024）という既存の制約と整合する
- ルームの時間設定を一覧で隠すことで、心理戦の要素を加える。入室して初めて条件が分かるという体験は、veryare の駆け引きの延長として位置づけられる
- room_actor がプロセスとして独立している既存設計（ADR 0006）により、ホストの離脱がルームの生死に直結しない。新しい仕組みを追加せずに実現できる

## 検討した代替案

- ホストが抜けたらルームも消える案。実装は単純だが、発表会中に作成者が離席した場合に遊べなくなるため、より運用に強い「ホスト非依存」を採用した
- 同時ルーム数を無制限にする案。実際に部屋を立てる人がちゃぴぃに限られる運用の下では管理上の意味が薄く、発表会の規模（最大3グループ）に合わせて上限を設けた

## 結果

- GameManifest（veryare）の minPlayers / maxPlayers を、それぞれ 2（鬼1+隠れ1）/ 5（鬼1+隠れ4）とする
- room_supervisor に、ゲーム種別ごとの同時ルーム数上限（veryare は3）を持たせ、上限到達時は新規作成を拒否する
- ルーム一覧UIは、探索フェーズの時間を表示しない
- room_actor はホストという概念を持つが、ホストの接続断・退出によってルーム自体を終了させない
