# ADR 0042: ステージの地図はサーバーが通知で配り、移動の規則と襖の状態をすべてのステージで共有する

- ステータス: 提案（下書き）
- 日付: 2026-10-09
- 関連: ADR 0009（契約は TypeScript を正とする）、ADR 0022（当たり判定）、ADR 0032（骨格とランダム間取り）、ADR 0033（襖と答え合わせタイム）、ADR 0035（性善説）、ADR 0039（固定ステージ「平屋」。下書き）。本 ADR は既存の ADR を書き換えない

## 文脈

ADR 0039（下書き）は、固定ステージ「平屋」について、壁と閉じた襖で移動が止まる規則をサーバーとクライアントで共有し、襖の開閉の状態をサーバーが持つと決めた。一方、ランダム間取りの骨格（ADR 0032）には、同じ決まりが無い。

いま、人間の移動は仮の ±5 m の正方形に丸められ、サーバーの地図（骨格の座標、1マス 1 m）と食い違っている。クライアントは骨格のデータを持たず、人間の鬼が開けた襖の状態もサーバーに届いていない。そのため、玄関からの出現（ADR 0032）、壁で止まる移動、射撃の見通し（ADR 0022 の簡易検証を超えて、issue-27 で作った壁の判定）が、実際のルームで働かない。また、鬼の通知の襖は `{corridor, slot}`（廊下とスロットの組）で表していて、部屋どうしの襖（ADR 0039）を表せない。

## 決定

**移動の規則は、すべてのステージで同じ**: 骨格（ADR 0032）にも、ADR 0039 と同じ移動の規則を使う。入力は、マスの大きさ・原点・各マスの領域・戸の一覧（隣り合う2マスの境と、種類: 襖・いつも開いている・いつも閉じている）・開いている襖の集合。異なる領域どうしの境は壁、戸の一覧の境は種類と開閉で通れるかが決まる。通れない境の手前で止め、境に沿って滑らせ、マスの角は両脇がどちらも通れるときだけ通す。骨格は、1マス 1 m・原点 (0, 0)・戸はスロットの襖だけ、として写す。

**ステージの地図は、サーバーが通知で配る**: サーバーは、選んだステージの地図のデータそのもの（マスの大きさ、原点、幅・奥行き、各行、部屋の割り当て、戸の一覧、リスポーン位置）を、veryare の通知として全員に送る。途中参加・再接続の人にも送る。クライアントは骨格や平屋のデータのコピーを持たず、通知の地図で表示し、同じ移動の規則で自分の移動を止める。サーバーの規則とクライアントの規則が食い違わないことは、共有の見本（移動の前後の位置 → 止まる位置）を両方のテストで読んで確かめる（ADR 0009 の考え方）。

**襖の状態はサーバーの1か所が持つ**: 開いている襖の集合を、ゲームの状態として1つだけ持つ。人間が開けた襖も、鬼 CPU が開けた襖も、ここに入る。移動の規則・射撃の見通し・鬼の通知は、すべてこの状態を使う。

**準備移動の開始時、襖は全部開いている**: 隠れ側が、襖を開けるボタンを押さずに部屋へ入れるようにする。ADR 0033 は、準備移動の開始時の襖の状態を定めていないため、ここで決める。その後は ADR 0033 のとおり、探索の開始で全部閉じ、答え合わせタイムの開始で全部開く。

開ける報告は、報告した人の位置が襖の境から 1.5 m 以内のときだけ受け付ける（骨格でも平屋でも同じ定数）。状態が変わるたびに、全員へ通知する。

**襖は、一般の境 `{a, b}` で指す**: 襖と戸は、隣り合う2マス `a`・`b` の組で指す。どちらが廊下かを決めない。鬼の通知の `openDoors` も、この形に切り替える。

**契約の変更は veryare の payload だけ**: 境・戸の種類・ステージの通知・襖の通知・開ける報告を、`packages/contracts/src/veryare.ts` に足す（鬼の通知の `openDoors` の型を変える）。`ClientMessage` と `ServerMessage` の外側は変えない。どれも共有の見本を作り、TS と Gleam の両方で読み込む。

## 理由

- 規則を1つにすれば、骨格で作った移動・襖・見通しの仕組みを、平屋（issue-44〜46）がデータを足すだけで再利用できる。二重に作らずに済む
- 地図をサーバーが配れば、クライアントにステージのデータの写しを持たせずに済み、サーバーとクライアントでデータが食い違うことが無い。平屋のように大きな地図でも、通知1回で足りる（1マスを1文字で表す）
- 準備移動の開始時に襖を全部開けておけば、20 秒の準備移動の中で、隠れ側が襖の前で立ち止まって開ける手間が無くなり、隠れ場所選びに時間を使える。隠れ側の通った跡は、探索の開始で全部閉じることで消える（ADR 0033 の一斉リセット）ので、鬼に手がかりは残らない
- 襖の状態が1か所にあれば、移動・見通し・表示・鬼 CPU が、同じ襖を同じ開閉として扱う。閉じた襖越しに見つける・撃つといった、ゲームの成立に関わる食い違い（ADR 0028）を防げる
- 一般の境は、廊下と部屋の襖も、部屋どうしの襖も、いつも開いている戸も、同じ形で表せる
- サーバーが移動の報告を規則で確かめるのは、誠実なクライアントとの食い違いを防ぐためで、不正対策のためではない（ADR 0035）

## 検討した代替案

- クライアントに骨格のデータの写しを持たせ、サーバーは骨格の番号と部屋の割り当てだけを送る案。通知は小さいが、Gleam と TS で同じデータを二重に持つことになり、食い違いの検算が要る。平屋で同じことをするなら、さらにもう1組の写しが要るため採用しない
- 骨格では移動を止めず、平屋だけ止める案。骨格のステージで壁を通り抜けられると、隠れ場所と見通しの意味が崩れるため採用しない
- 鬼 CPU の襖を、鬼 CPU だけの状態のまま残す案。人間に見える襖と、鬼 CPU が通れる襖が食い違うため採用しない

## 結果

- issue-29a で、移動の規則（すべてのステージ共通）、玄関へのリスポーン、ステージの通知を作る
- issue-29b で、襖の状態・開ける報告・襖の通知を作り、鬼 CPU の襖をまとめ、射撃の見通しを有効にする
- issue-29c で、クライアントが通知の地図から仮素材の表示を組み、同じ移動の規則で動く
- issue-44 は、平屋のデータ（0.3 m の格子と3種類の戸）を足すだけで、移動と襖の仕組みを再利用する。issue-45 は見通しを戸の一覧へ一般化し、issue-46 は issue-29c の表示をフォールバックに使う
