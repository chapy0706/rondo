# ADR 0046: フェーズの通知の長さは、通知を作った時点からの残りとする

- ステータス: 提案（下書き）
- 日付: 2026-10-16
- 関連: ADR 0024（フェーズとタイマー）、ADR 0013（再接続猶予）。購読者に届ける状態（`server/src/rondo_server/games/veryare/room.gleam` の `subscriber_snapshot`）の続き。本 ADR は ADR 0024 を書き換えない

## 文脈

veryare のフェーズの通知（`{ type: "phase", phase, durationMs, area, oni, outcome }`）の `durationMs` は、フェーズの長さだった。画面は、通知を受け取った時刻から数え始め、「長さ − 受け取ってからの経過」を残り時間として出す。

途中参加と復帰（再読み込み・再接続）のとき、サーバーはフェーズの通知を本人宛てに送り直す（CPU ありのルームで、途中参加の人にフェーズが届かなかった不具合の直しで、送り直しにフェーズを入れた）。送り直しの `durationMs` がフェーズの長さのままだと、画面はフェーズが始まったばかりだと思い、残り時間が長めに出る。

- スマホの画面ロックのあとの再接続で、残り時間の表示が正しくならない
- 塗りの自動確定（終わりの 2 秒前）が、画面の残り時間で動くので、ずれると、サーバーのペイントフェーズが先に終わり、ペイントが送られない

## 決定

フェーズの通知の `durationMs` は、「通知を作った時点からの、フェーズの残り」とする。

- フェーズの開始のときの通知は、残り = フェーズの長さ。これまでと同じ値
- 送り直し（途中参加・復帰）のときだけ、残り = 長さ − フェーズの開始からの経過（0 未満にしない）
- サーバーは、ルームの中（状態機械の外）に、いまのフェーズの開始時刻（単調に増える時計）を持ち、step が進むたびに覚え直す。時計は、テストで差し替えられる（`room.spec_with_clock`。フェーズ時間の短縮と同じく、ルームの設定に渡す）
- 画面は、受け取った時刻から、届いた残りを数える（`apps/web/src/games/veryare/phaseClock.ts`）。中身の同じ通知（長さも同じ）は無視する。長さが違えば、新しい通知として、残りを届いた値に合わせ直す
- 長さを持たないフェーズ（鬼選出・終了）は、これまでどおり null

契約の型は変わらない（`durationMs` は、これまでどおり数か null）。変わるのは値の意味だけ。

## 理由

- 画面の数え方（受け取った時刻からの経過を引く）を変えずに、送り直しの残りが正しくなる。フェーズの開始の通知の値は同じなので、これまでの画面とボットは、そのまま動く
- 契約に「残り」の欄を足す案より、送る物が増えず、型も変わらない
- 勝敗とフェーズの遷移は、これまでどおりサーバーのタイマーが決める。開始時刻は、送り直しの値を作るためだけに使う

## 影響

- 画面で、長さを「フェーズの全体の長さ」として使っている所は無い（残り秒数の表示、ペイントの板のロック、塗りの自動確定、塗れるかの判定は、どれも残りを使う）。答え合わせの点滅の位相は、受け取った時刻から数えるので、送り直しで受け取り直すと、位相だけがずれる（見た目の 1 秒周期の点滅で、遊びには関わらない）
- 通信の遅れのぶん、画面の残りは、サーバーの残りより少しだけ長い（これまでの開始の通知と同じ）

## 検討した代替案

- 契約に残りの欄（`remainingMs`）を足す案。型が変わり、契約のテストと画面とボットの読み方を変える必要があるため採らない
- 送り直しでは、フェーズの通知を送らない案。途中参加・復帰の人に、フェーズとエリアが届かない不具合に戻るため採らない
