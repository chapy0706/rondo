# 負荷・長時間・乱れた通信・不正な入力の試験（issue-51）

ブラウザを使わず、ボット（issue-49）の仕組みで、実際の Gleam サーバーに対して試す。試験の道具は `bots/src/trials/`、動かし方は `tools/load.sh`。

## 実行

```bash
./tools/load.sh limits                 # 上限（同時ルーム数3・定員5人・空きが戻ること）
./tools/load.sh load --seconds 30      # 3ルーム × 5人の同時負荷（待機ルームの同期を含む）
./tools/load.sh chaos --rounds 30      # 乱れた通信（切断と復帰、猶予切れ、他人のトークン）
./tools/load.sh garbage                # 不正な入力（壊れた JSON・未知の種別・バイナリ・深い入れ子・大量送信）
./tools/load.sh soak --minutes 60      # 長時間の放置（待機ルームで、つなぎ続ける）
./tools/load.sh join                   # 参加・復帰の組み合わせ表（途中参加の人に、いまの状態が届くか。下の「参加・復帰の組み合わせ表」）
./tools/load.sh spectate --seconds 20  # 観戦ルーム（観戦者 20 人）と人間の 3 ルーム × 5 人を同時に（issue-67。下の「観戦ルーム」）
./tools/flood.sh                       # 極端に大きな1通（80 MiB。issue-51 で先に入れた手当ての確認）

# サーバーを立てない確かめ（issue-67。ルームを直接動かす。下の「観戦ルームの長めの確認」）
cd server && RONDO_SOAK_MINUTES=30 gleam run -m rondo_server/spectate_soak
```

- どれも、開発用のサーバー（3000番）と別に、3300番で Gleam サーバーを起動し、終わったら止める（`tools/bots.sh` と同じ）。フェーズ時間は 1/20 に縮める。再接続猶予（10 秒）とハートビート（20 秒）は縮まない
- サーバーのプロセス（待ち受けのポートのプロセス）を調べ、`ps` で RSS と CPU を読む
- サーバーの出力は一時ファイルに取り、終わりに「受信プロセスが落ち」「CRASH REPORT」「ERROR REPORT」の行の数を出す。試験の後にサーバーが応答しなければ、失敗にする
- 終了コードは、全部通れば 0、失敗があれば 1、使い方の誤り・起動の失敗は 2
- `make verify` には含めない（サーバーの起動を伴うため）。集計と確かめの部分（`bots/src/trials/stats.ts`・`views.ts`、ボットのクライアントの口）は単体テストにして、`make verify` で動く
- Makefile には入れていない（Makefile は検証の定義のため、足すかは人が決める）

## 結果

### 上限（`./tools/load.sh limits`）

| 確かめ | 結果 |
| --- | --- |
| 4つ目のルームは断られる（room-limit） | 通過 |
| 5人目までは入れ、6人目は満員で断られる（room-full） | 通過 |
| 退出で、1人だけのルームが消え、空きが戻る | 通過 |
| ゲームが終わったルームに人が残っている間も、空きが戻る | 通過（直した後。下の「見つかった問題」1） |
| 試験の後も、サーバーは別の接続とふつうに話せる | 通過 |

### 同時負荷（`./tools/load.sh load --seconds 30`）

3ルーム × 5人（15接続）が、待機ルームで 50 ms ごとに歩き続け（向きも変わる）、ときどき待機ポーズを変える。歩き続けたまま、各ルームの作った人が同時に中央の円に触れる。

| 項目 | 最小 | 中央 | 95% | 最大 |
| --- | --- | --- | --- | --- |
| 1接続が受け取るメンバーの通知（通/秒） | 6.5 | 6.5 | 6.5 | 6.5 |
| メンバーの通知1通の大きさ（バイト。JSON を取り直した大きさ） | 601 | 624 | 627 | 628 |
| 1接続が受け取る全電文（バイト/秒） | 4048 | 4049 | 4070 | 4070 |
| カウントの開始が届くまで（ms。送ってから） | 1 | 2 | 3 | 3 |
| 同じルームの5人に届く時刻の差（ms） | 0 | 0 | 0 | 0 |

| サーバー | 値 |
| --- | --- |
| RSS の始め・最大・終わり（MiB） | 82.0・96.5・93.1 |
| CPU の平均・最大（%） | 10.6・15.7 |

- 1ルームが送るメンバーの通知は、約 32.4 通/秒（6.5 通/秒 × 5 宛先）。目安の 50 通/秒以下
- issue-59 の見積もり（`server/test/rondo_server/games/veryare/waiting_traffic_test.gleam`）との比べ: 見積もり 約 6.7 回/秒・1通 629〜633 バイト・1接続 約 4.2 KB/秒に対し、実測 6.5 回/秒・中央 624 バイト・約 4.0 KB/秒。実測の送る間隔は、150 ms のタイマーと、次の動きの報告（50 ms ごと）の重なりで、少し長くなる
- 待機の通知が混ざっても、フェーズの通知（カウントの開始）は 3 ms 以内に届いた

### 乱れた通信（`./tools/load.sh chaos --rounds 30`）

| 確かめ | 結果 |
| --- | --- |
| 猶予内（2 秒後）に、同じプレイヤーとして同じルームへ戻れる | 通過 |
| 猶予内の切断は、ほかの人に伝わらない（player-left が届かない） | 通過 |
| 猶予を過ぎると離脱が確定する（切ってから 10.0 秒で player-left） | 通過 |
| 猶予切れの後は、戻れない（reconnect-failed） | 通過 |
| つながっている人のトークンでは、戻れない（reconnect-failed）。持ち主はルームに残る | 通過 |
| ランダムな切断と、0.3〜3 秒後の復帰を 30 回くり返して、毎回戻れる | 通過 |
| 乱れたあと、全員が見ている参加者が同じで、実際の人数（4人）と、一覧の人数とも合う | 通過 |
| 乱れたあとも、立候補でカウントの開始が全員に届く | 通過 |

### 不正な入力（`./tools/load.sh garbage`）

攻撃役の接続から、次の 16 種を送る: 空の文字列、JSON でない、閉じていない JSON、配列、null、type が無い、type が数、未知の種別、項目の型が違う、別のルーム宛てのゲーム内イベント、形の違うゲーム内イベント、極端な数（1e308）、JSON で書けない数（1e400）、深い入れ子（10 万段）、深い入れ子のゲーム内イベント（10 万段）、バイナリ（1 KiB）。続けて、別の接続から 1 万通（移動・一覧・未知の種別・待機ポーズ・いいね）を、待たずに送る（80 ms で送り終わる）。

| victim（同じルームの別の利用者）の list-rooms の往復（ms） | 中央 | 95% | 最大 | 届かなかった |
| --- | --- | --- | --- | --- |
| 送る前 | 1 | 1 | 1 | 0 |
| 大量送信の間 | 0 | 1 | 83 | 0 |
| 大量送信の後 | 0 | 1 | 2 | 0 |

| 確かめ | 結果 |
| --- | --- |
| 壊れた・形の違う電文の後も、別の利用者は話せる | 通過 |
| 大量送信の間も、別の利用者の往復はすべて返る | 通過 |
| 大量送信の後、往復は送る前の水準に戻る | 通過 |
| 不正な入力の後も、victim のルームは進む（立候補でカウントが始まる） | 通過（直した後。下の「見つかった問題」2） |
| サーバーのログに、CRASH REPORT が出ない | 通過（直した後） |

- サーバーの RSS は、大量送信で 83.6 → 133.0 MiB に上がり、終わりに 129.1 MiB（BEAM が確保したメモリを、すぐには返さないため）。長時間で増え続けるかは、下の「長時間の放置」で見る

### 極端に大きな1通（`./tools/flood.sh`）

80 MiB の1通を送ると、ソケット1本のメモリの上限（64 MiB / `server/src/rondo_server/connection/heap_guard.gleam`）で、その接続だけが閉じられた（送信から約 0.3 秒）。サーバーのログに「受信プロセスが落ちました」の1行が出て、別の接続はふつうに話せた。最後の砦は、コンテナのメモリ上限（`docker-compose.server.prod.yml` の `mem_limit: 1g`）と、自動再起動（`restart: unless-stopped`）。

### 長時間の放置（`./tools/load.sh soak --minutes 5`。ローカル）

| 確かめ | 結果 |
| --- | --- |
| 5 分の間、切断が起きない（5人とも） | 通過 |
| ping が、およそ 20 秒ごとに届き続ける（5 分で 15 回ずつ） | 通過 |
| 放置のあとも、同じルームで話せる（立候補でカウントが始まる） | 通過 |

- RSS は 89.6 → 26.3 MiB に下がった。macOS は、使われていないメモリを圧縮・退避するので、何もしない間は RSS が下がる。この数だけでは「増え続けない」の確かめとしては弱いので、1時間の放置は、Linux（A1）で測る（下の手順）
- 1 時間の放置（`--minutes 60`）は、手元でも本番でも、まだ流していない（下の手順で、人が流す）

### 参加・復帰の組み合わせ表（`./tools/load.sh join`）

CPU ありのルームに 2 人目が入ると、フェーズの通知（エリアの色を含む）が届かず、移動パッドと鬼希望エリアが出なかった不具合の、同じ種類の見落としを見つける。表は `bots/src/trials/joinMatrix.ts`（単体テストつき）、回すのは `bots/src/trials/join.ts`。`--only 鬼 CPU` のように、名前の一部で絞れる。

- 軸: CPU（なし・隠れ側 1 体・隠れ側 2 体・鬼 CPU）、参加の順番（作った人・2 人目・3 人目）、参加の時機（待機・カウント中・準備移動・ペイント・探索・答え合わせ・結果のあと / issue-70）。実際に起こりうる組み合わせだけ（カウントと鬼選出の後は、2 人以上のときだけ）
- 広い屋敷の構成（issue-65）: CPU なしの組み合わせを、広い屋敷だけ（`{ stage: 3 }`）のルームでも回す（名前は「広い屋敷・」で始まる。`--only 広い屋敷` で絞れる）。どの組み合わせでも、いちばん新しいルーム情報の探索時間が、ふつうは 40 秒、広い屋敷は 120 秒（+80 秒）であることも確かめる
- 鬼選出の間の参加: 参加した人に届いた通知の種類（ステージ・襖・フェーズ・メンバー・ルーム情報）と、フェーズの中身（フェーズ・エリアの色・鬼）が、作った人の最後のものと同じ。続けて、つなぎ直す（復帰）と、もう一度同じものが届く
- 結果のあと（issue-70）: 参加はサーバーが断る（`game-already-started`）。作った人がつなぎ直すと、結果（`game-ended`）が、閉じるまでの残り（`closesInMs`。0 より大きい）つきで送り直される（`resentResult`）。結果のあと 9 秒（縮めた 3 分）でルームは閉じるので、その前につなぎ直す
- 鬼選出の後の参加: サーバーが断る（`game-already-started`）。作った人がつなぎ直すと、その時機の状態（探索・答え合わせでは、隠れ側の一括配信・まだ隠れている人・鬼の通知も）が届き、フェーズの中身が、つなぎ直す前と同じ
- 作った人: 作成で届いた状態（ステージ・襖・フェーズ・ルーム情報。メンバーの通知は、変わったときだけ送る（ADR 0044）ので、1 人だけの作成の時点では届かない。自分しか載らない一覧で、画面は自分を除くので、届いても空と同じ）。2 人目が入ると、作った人にも、2 人が載ったメンバーの通知が届く。つなぎ直して届く状態は、つなぎ直す前に持っていたものと同じ
- 結果: まだ流していない（手元で `./tools/load.sh join` を流して、表を貼る）

### 観戦ルーム（`./tools/load.sh spectate`。issue-67）

人間の 3 ルーム × 5 人（15 接続）が待機ルームで歩き続ける中で、観戦ルーム（隠れ CPU 4 体、観戦者 20 人）を動かし、人間の対戦の応答が遅れないことと、ボットの観戦者が受け取る観戦用の通知が正しいことを確かめる（`bots/src/trials/spectate.ts`）。

- 往復の時間: 別の利用者の `list-rooms` の往復を、観戦ルームを作る前と、観戦ルームと同時に、30 回ずつ測る。同時の 95% が、前の 95% + 50 ms 以内
- カウントの開始の遅れ: 歩き続けたまま、各ルームの作った人が中央の円に触れ、カウントの開始が 15 接続すべてに 500 ms 以内（95%）に届く
- 観戦用の通知: 観戦者 20 人とも、全員の位置・色・ポーズ・間隔が正しく（`bots/src/spectate.ts`）、次の試合が 2 回始まっても、受け取り続ける。観戦ルームが送る通知は 200 通/秒以下
- 結果: まだ流していない（サーバーを起動するので、手元で `./tools/load.sh spectate` を流して、表を貼る）

参考（サーバーのテストで測った値 / `server/test/rondo_server/games/veryare/spectate_traffic_test.gleam`）: 観戦者 20 人、隠れ CPU 4 体が歩く準備移動で、1 人あたり毎秒 10 通、ルーム全体で毎秒 200 通。1 通は 380 バイト（5 人ぶんで 481 バイト、色とポーズつきの 1 通で 831 バイト）。

### 観戦ルームの長めの確認（`gleam run -m rondo_server/spectate_soak`。issue-67）

サーバーを立てず、ルーム（`room_actor`）を直接動かす。観戦ルーム（隠れ CPU 4 体、探索 100 秒）を、時間を 1/100 に縮めて（`RONDO_SOAK_DIVISOR`。既定 100）、連続の試合で回し続ける。観戦者は、送信先を持つプロセス 20 個。1 分ごとに、プロセスの数・ルームのメモリ（ごみ集めのあと）・全体のメモリ・観戦者への通知の間隔を表で出し、最後に判定する（`spectate_soak.problems`。単体テストつき）。

- プロセスの数: 最後の分が、最初の分より 10 以上多ければ、問題
- ルームのメモリ（ごみ集めのあと）: 最後の分が、最初の分の 2 倍を超えれば、問題
- 通知の間隔: どの分でも、最小が 80 ms 未満（100 ms ごとの確かめより明らかに短い）か、中央の値が、最初の分から大きくずれれば（1.5 倍 + 20 ms を超えるか、2/3 - 20 ms を下回る）、問題
- 時間を 1/100 にすると、準備移動が 0.2 秒になり、隠れ CPU は歩かない（時間内に着ける隠れ場所が無いので、①の歩きを決めず、これまでどおり直接置く）。通知は主に、鬼 CPU の 0.5 秒ごとの歩き（縮めない）で出るので、間隔は 100 ms より長い。歩く間の 100 ms ごとの間隔は、`spectate_traffic_test.gleam` と `./tools/load.sh spectate` で確かめる

### 観戦ルームの設定のシミュレーション（`make simulate`。issue-67）

観戦ルームと同じ始まり方（鬼 CPU 1 体、歩く隠れ CPU 4 体、ランダム間取り 10 種、鬼選出なし）で、鬼 CPU の強さ × 探索の時間ごとに 300 試合（10 種 × 30 の種）を回した、鬼の勝率。異常（ADR 0028 と、4 体とも道が決まる・準備移動の時間内に着く・被らない）は 0 件。

| 強さ | 探索 40 秒 | 60 秒 | 80 秒 | 100 秒 |
| --- | --- | --- | --- | --- |
| よわい | 0% | 0% | 1% | 2% |
| ふつう | 1% | 3% | 8% | 13% |
| つよい | 7% | 19% | 32% | 37% |

- 40〜60% に収まる組み合わせは無かった。最も近い「つよい・100 秒」（37%）を、観戦ルームの既定にした（`veryare.spectate_strength`・`spectate_default_exploration_seconds`、web の `VERYARE_SPECTATE_OPTIONS`）
- 鬼が勝つには、隠れ CPU 4 体を、すべて見つけなければならない。つよい・100 秒でも、見つかるのは平均 3.2 人で、全員を見つける前に時間が切れることが多い
- 表の外の「つよい・120 秒」（ルームで選べる最長）は、同じ回し方で 45.7%（300 試合）で、40〜60% に収まる。既定を 120 秒にするか、隠れ CPU の既定の数を減らすかは、人が決める

## 見つかった問題と、直したこと

1. **ゲームが終わったルームに人が残っている間、同時ルーム数に数えられたままだった**（上限の試験）。結果画面のまま置かれると、新しいルームを作れない。ゲームが終わったルームは、同時ルーム数に数えないように直した（ADR 0045 下書き）。再現の試験: `server/test/rondo_server/room/room_directory_test.gleam` の `finished_room_does_not_count_toward_the_limit_test`
2. **移動の報告で、極端な座標（1e308 など）を送ると、ルームのプロセスが落ちた**（不正な入力の試験）。待機ルームの円に丸める計算（x × x）が桁あふれし、その部屋の全員が遊べなくなる。座標の絶対値が 1000 m を超える報告は、無視するように直した（`game.max_coordinate`）。再現の試験: `server/test/rondo_server/games/veryare/move_bounds_test.gleam`。ほかのクライアント由来の数（ペイントの u・v とブラシの大きさ、向き）は、すでに範囲を確かめるか、巻き取っていた

## 電文の大きさと送信の頻度の上限（提案）

- 大きさ: ソケット1本のメモリの上限（64 MiB）と、コンテナのメモリ上限で、足りている。正しいクライアントの電文は数十 KB までなので、さらに小さい上限（例: 1 MiB）を足す余地はあるが、mist の受信は、つながった後にしかアプリへ届かないため、手前で止めるには mist の設定か、手前のプロセスが要る。発表会までは足さない
- 頻度: 1つの接続から 1 万通を 80 ms で送っても、別の利用者の往復は 1 ms 前後のまま（最大 83 ms）で、ほかのルームに波及しなかった。各接続とルームが別のプロセスなので、1つの接続の大量送信は、その接続とそのルームの順番待ちに留まる。発表会までは、送信の頻度の上限は足さない。必要になったら、接続ごとに「1 秒あたりの電文の数」を数えて、超えた分を捨てる形を、connection の層に足す

## 本番（Cloudflare 経由）での手順

本番への試験は、短時間の確認に限る。流すかどうか、いつ流すかは人が決める。継続的な負荷はかけない。

### 1時間の放置（issue-51 の「長時間の放置」）

1. 手元の端末から、本番の WebSocket の URL へ、ボットを直接つなぐ（サーバーは立てない）。
   ```bash
   pnpm --filter @rondo/bots exec node src/trials/soak.ts --minutes 60 --url wss://<本番のホスト>/ws
   ```
2. 同じ時間、A1 の上で、サーバーのコンテナのメモリを記録する（1 分ごと）。
   ```bash
   while true; do date '+%H:%M:%S'; docker stats --no-stream --format '{{.Name}} {{.MemUsage}} {{.CPUPerc}}' rondo-ws; sleep 60; done | tee soak-$(date +%Y%m%d).log
   ```
3. 確かめること: ボットの表の「切断が起きない」「ping が、およそ 20 秒ごとに届き続ける」「放置のあとも、同じルームで話せる」が通過する。A1 のメモリが、1時間で増え続けていない（始めと終わりの差が数 MiB 程度）
4. 結果（ボットの表と、メモリの記録の最初と最後の行）を、この文書の「結果」に足す

### 手元（Linux）での1時間の放置

```bash
./tools/load.sh soak --minutes 60
```

macOS では RSS が下がって見えるので、メモリの増え方は Linux（A1 の上でサーバーを別のポートで立てる、など）で見る。

### 本番で流さないもの

- `load`・`chaos`・`garbage`・`flood` は、本番に向けない（公開しているサービスに負荷をかける）。`tools/flood.sh` は、localhost 以外へは `--allow-remote` を付けないと動かない
